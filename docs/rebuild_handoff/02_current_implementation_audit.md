## 3. 性能问题与证据

### P0：首屏串行依赖和重复刷新

- `pages/home/index.js:onShow()` 每次回到首页都调用 `refresh()`。
- 登录态先请求 `/api/v1/user/state`，再按 view 顺序加载活动、打卡或日常数据。
- 活动首页虽并行读取 profile/campaign/task/product，但必须在 user state 返回后才开始。
- 登录成功后 `submitLogin()` 再次调用完整 `refresh()`；健康同意返回也会重复刷新。

影响：弱网或 Cloud Container 冷启动时，用户先等待身份状态，再等待第二批内容；返回首页会重复产生相同瀑布。

### P0：超时过长且缺少快速降级

- Cloud Container 默认超时为 30 秒。
- 页面没有统一请求取消、页面离开取消、相同请求合并或 stale-while-revalidate 缓存。
- 单一非关键区块失败可能拖慢整个视图完成。

影响：用户会感知为“按钮无响应”或“小程序很慢”，即使后端最终成功。

### P0：首页 Module 过浅、页面 Implementation 过宽

- `home/index.js` 650 行、WXML 308 行、WXSS 910 行。
- 一个 Page 同时知道身份、注册问卷、健康同意、活动、任务、商品、7 日打卡、优惠券、退款和日常趋势的细节。
- 删除该页面不会消除复杂度，复杂度会散落到全部流程，说明需要重新建立深 Module，而不是继续拆小函数后保持同一 Interface。

### P1：包和资产策略缺少预算

- 上传总包约 564.1 KB，主包约 412.1 KB，当前不算大；问题主要是运行时请求和渲染，不是总包大小。
- 大图尚未正式进入仓库。若直接加入原始 PDF/PNG，会迅速放大主包、解码时间和内存。
- 缺少 WebP/AVIF（微信实际兼容性需真机验证）、多尺寸裁切、CDN 缓存和首屏占位策略。

### P1：缺少真实性能证据

当前没有以下基线：

- 冷启动/热启动首个可交互时间；
- 登录点击到反馈、到身份完成、到首页可用的 P50/P90/P95；
- `/user/state`、首页聚合数据和图片请求瀑布；
- Cloud Container 冷启动率、错误率和超时率；
- iOS/Android 中低端真机分位数。

因此不能只凭“感觉慢”选择重写技术栈；第一切片必须加入可观测性并形成前后对照。

## 4. 后端现状

### 可保留的深 Module

- 微信身份与会员关联；
- 隐私同意和健康数据保留；
- 活动内容、场次、报名与审核；
- 任务事件、奖励和结算事实；
- 命令幂等、结果保护、Outbox/Inbox、重放和 fencing；
- MySQL 迁移、发布证据和运营审计；
- 外部平台 Adapter 与人工复核。

### 需要重构的集中点

- `backend/src/app.js` 约 2,578 行，路由装配、鉴权、输入解析、Presenter 和业务协调集中。
- 首页客户端需要理解多个后端 Interface，缺少面向移动首屏的深查询 Module。
- 运行、迁移、发布和业务源文件很多，但缺少面向新开发者的 Module 地图和依赖方向验证。
- 运营后台已经覆盖大量能力，前台不应再次创建平行事实源。

## 6. 不应在重构中丢失的回归场景

1. 未勾选协议点击登录必须给明确反馈。
2. 登录成功后首页读取失败不能清除有效身份或无提示退回 Guest。
3. 健康同意拒绝/撤回后商品、活动和人工协助仍可用。
4. 活动重复报名、并发最后名额、取消和结果未知必须保持幂等。
5. 任务重复提交不能重复完成、发券或结算。
6. 红旗健康回答不能进入普通建议或推荐。
7. 旧 7 日计划用户必须通过兼容 Adapter 继续完成历史流程。
8. CloudBase、MySQL、微信审核和线上发布继续保持独立 Gate。
