## 1. 文件效力与结论

本文件把小程序性能从开发建议转为候选版本准入条件。正式上线版本采用“性能预算 + 发布 Gate”的均衡档方案：首屏和核心操作必须足够快，同时保留已经批准的品牌视觉、内容表达、健康安全规则和交互过渡。

本文件只定义小程序性能要求。Element Plus Admin 运营后台的性能要求另行设计，不在本文件中混合处理。

本文件不证明当前代码已经满足指标，也不代表已经部署、迁移、上传微信、送审、发布或切换线上流量。真实素材体积、目标机型和真实接口数据仍需在实施与候选版本阶段验证。

## 2. 设计原则

1. **正式上线均衡档**：不追求牺牲体验的极限数字，也不接受“能打开即可”。
2. **预算前置**：包体、图片、请求、渲染、内存和页面旅程都有开发阶段预算。
3. **真机结论**：开发者工具只用于定位问题，最终验收以 iOS 和 Android 真机为准。
4. **先删旧债**：不优化即将删除的任务、打卡、奖励、内部订单、退款和旧 Job；按正式上线切片重建后再测量。
5. **状态真实优先**：弱网可以降低图片清晰度和内容新鲜度，不得伪造登录、健康结果、注册或报名状态。
6. **UED 不被性能替代**：不得通过删除已批准文案、内容、主要动画或布局来制造达标结果。
7. **发布状态分离**：本地验证、候选版本、微信上传、审核、正式发布和线上观察分别留证。

## 3. 指标定义与总体验收目标

### 3.1 指标定义

- `appLaunch`：用户启动小程序到首个页面最大内容绘制结束；
- `route`：用户触发页面跳转到目标页面最大内容绘制结束；
- `firstRender`：页面收到路由到 `onReady`；
- 首个可理解内容：用户已经能识别当前页面是什么、可以做什么，不要求所有高清图片加载完成；
- P75：75% 的样本快于或等于该值，是本项目主要验收口径；
- P95：用于发现少量用户的严重慢体验，不替代 P75。

微信官方指标定义参考：[性能数据](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/perf_data.html)。

### 3.2 总体性能目标

| 场景 | iOS P75 | Android P75 | 说明 |
| --- | ---: | ---: | --- |
| 本地包冷启动 `appLaunch` | ≤ 1.2 秒 | ≤ 2.6 秒 | 本机已有可用代码包 |
| 下载或更新代码包冷启动 | ≤ 1.8 秒 | ≤ 3.7 秒 | 单独统计下载/更新状态 |
| 首个可理解内容 | ≤ 0.9 秒 | ≤ 1.4 秒 | 不等待非关键高清资源 |
| 首页首张主视觉完整显示 | ≤ 1.8 秒 | ≤ 2.5 秒 | 包含当前轮播图和文案 |
| 已加载 Tab 切换 | ≤ 400ms | ≤ 600ms | 首页、健康、活动、我的 |
| 首次进入分包页面 | ≤ 1.2 秒 | ≤ 1.5 秒 | 标准网络 |
| 弱网首次进入分包页面 | ≤ 2.0 秒 | ≤ 2.5 秒 | 使用本文件弱网档位 |

其他交互底线：

- 点击后 100ms 内出现视觉反馈；
- 200ms 内无法完成的操作必须显示结果状态或加载状态；
- 列表、沉浸式详情与问卷页面滚动流畅度 P75 不低于 50 FPS；
- 不允许持续超过 200ms 的界面冻结。

微信官方启动性能建议参考：[启动性能](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/tips/start.html)。本项目目标是候选版本预算，不应被解释为微信平台对每台设备的结果承诺。

### 3.3 统一测量规则

- Android 与 iOS 分开统计；
- 本地包、首次下载、版本更新分开统计；
- Wi-Fi、标准 4G、弱网和离线恢复分开统计；
- 按入口页、设备档位、基础库和版本号保留维度；
- 每个核心场景至少执行 30 次，P75 为主要结论，同时记录 P95；
- 每次候选版本必须覆盖完整核心旅程，不以单个首页成绩代表整个小程序。

## 4. 代码包与资源预算

### 4.1 代码包预算

代码包体积以微信构建产物报告为准，图片体积以实际传输文件为准，`1KB = 1,024 bytes`、`1MB = 1,024KB`。单次发布新增体积指全部代码包相对最近批准基线的净增长。

| 项目 | 目标值 | 硬上限 |
| --- | ---: | ---: |
| 主包 | ≤ 1.3MB | 1.5MB |
| 单个分包 | ≤ 800KB | 1.2MB |
| 全部分包合计 | ≤ 6MB | 8MB |
| 主包本地媒体资源 | ≤ 200KB | 300KB |
| 单次发布新增体积 | ≤ 100KB | 超出必须解释并重新批准 |

微信单个代码包平台上限和分包机制参考：[代码包体积优化](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/tips/start_optimizeA.html)。项目硬上限比平台上限更严格，平台允许上传不代表项目允许发布。

### 4.2 分包规划

主包只放置：

- 欢迎页结构与轻量首屏回退资源；
- 四个 Tab 入口页与导航外壳；
- 首页；
- 登录页；
- 共享样式和首屏必需 Module。

分包按正式上线旅程组织：

- 健康分包：初始化建档、评测、结果；
- 活动分包：沉浸式详情、报名确认；
- 我的分包：关于、隐私、注销等低频页面。

实施规则：

- 为用户下一步最可能进入的分包配置预下载；
- 使用 `lazyCodeLoading: requiredComponents`；
- 低频 UI 不得声明为全局依赖；
- 不保留旧任务、打卡、奖励、订单、退款代码和资源；
- 欢迎页与首页的高清背景图不进入主代码包，首屏先使用轻量回退视觉，再加载 CDN 资源；
- 分包拆分不改变用户路由、返回行为或高保真图。

按需注入参考：[代码注入优化](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/tips/start_optimizeB.html)。

### 4.3 图片预算

| 素材类型 | 目标值 | 硬上限 |
| --- | ---: | ---: |
| 欢迎页单张背景图 | 300–450KB | 600KB |
| 首页首张轮播图 | 300–450KB | 600KB |
| 首页后续轮播图 | ≤ 350KB | 500KB |
| 活动列表封面 | ≤ 120KB | 180KB |
| 沉浸式详情单张图片 | ≤ 400KB | 600KB |
| 用户头像 | ≤ 80KB | 150KB |
| Logo 或 Tab 图标 | ≤ 20KB | 40KB |

首屏同时发起的图片下载总量目标不超过 800KB。所有图片必须：

- 按实际显示尺寸由 CDN 输出，不下载原始大图；
- 优先 WebP，并保留平台兼容回退格式；
- 在显示前固定宽高比，避免布局跳动；
- 首张优先，后续轮播、详情长图和列表屏外图片懒加载；
- 使用带版本号的长期缓存，发布新素材时主动换版本；
- 失败时保留稳定占位、轻量回退或最近一次成功缓存，不出现白屏。

运营后台在素材上传前必须检测尺寸和体积，超出硬上限时禁止发布。

## 5. 网络、响应与缓存预算

### 5.1 页面请求规则

| 页面 | 请求规则 |
| --- | --- |
| 欢迎页 | 不发起登录、会员、健康等业务数据请求；高清视觉资源可以独立加载 |
| 首页 | 首屏最多一个内容请求；不请求用户、健康或会员数据 |
| 活动列表 | 一个分页列表请求；游客只返回公共内容，登录用户的报名状态由同一响应批量返回 |
| 活动详情 | 最多两个并行请求：详情内容与受保护的报名状态 |
| 健康访客页 | 只读取公共内容；受保护状态在登录后读取 |
| 我的访客页 | 不请求私密资料；登录后合并读取资料 |

并行网络请求通常不超过 4 个。切换页面后取消已经失效的请求；`onShow` 不重复发起相同请求；相同参数的并发读取需合并；列表必须分页。

### 5.2 后端响应预算

| 类型 | P75 | P95 | 超时与恢复 |
| --- | ---: | ---: | --- |
| 公共读取 | ≤ 600ms | ≤ 1.2 秒 | 8 秒后明确失败 |
| 登录后读取 | ≤ 800ms | ≤ 1.5 秒 | 8 秒后明确失败 |
| 注册、提交、报名等写入 | ≤ 1 秒 | ≤ 2 秒 | 12 秒后进入结果未知恢复 |

写入超时不得直接提示成功或失败。客户端通过幂等标识和权威状态查询恢复最终结果，避免重复注册、重复问卷记录或重复报名。

### 5.3 响应体预算

| 响应 | 压缩后目标值 |
| --- | ---: |
| 首页发布内容 | ≤ 100KB |
| 活动列表单页 | ≤ 100KB，10–20 条 |
| 共用详情元数据 | ≤ 100KB |
| 用户资料 | ≤ 30KB |
| Root4U 状态与生活方式建议 | ≤ 80KB |

响应只返回当前页面所需字段。不得返回未使用素材、完整健康原始答案、无关会员资产或所有历史量表版本；问卷只下发当前已发布版本。

### 5.4 缓存规则

- 首页、活动、公共详情使用“先展示最近缓存、再后台更新”；
- 公共内容按发布版本失效，不按固定时间盲目覆盖；
- 已知已撤下、已到期或已失效的内容必须从缓存移除，不得因离线继续展示；
- 报名状态最多缓存 30 秒，关键操作后必须读取权威状态；
- 登录资料只做必要的会话级缓存；
- 健康原始答案不得作为普通长期缓存保存；
- 退出登录清除私密资料、健康和受保护状态缓存，保留欢迎页状态、公共内容和图片缓存；
- 缓存损坏时回退网络，不允许造成循环启动或白屏。

## 6. 运行时渲染、动画与内存

### 6.1 `setData` 预算

| 项目 | 目标值 | 硬上限 |
| --- | ---: | ---: |
| 单次普通 `setData` 数据量 | ≤ 20KB | 64KB |
| 单次用户操作触发次数 | ≤ 2 次 | 3 次 |
| 持续更新频率 | ≤ 5 次/秒 | 10 次/秒 |
| 首次渲染批次 | ≤ 3 次 | 5 次 |

Implementation 必须：

- 只更新发生变化且参与渲染的字段；
- 合并同一轮更新；
- 不使用 `this.setData(this.data)`；
- 不把完整响应对象或大对象直接放进渲染数据；
- 不在 `onScroll` 中逐帧更新；
- 不使用毫秒级计时器刷新界面；
- 页面进入后台、隐藏或卸载时停止更新。

官方建议参考：[合理使用 setData](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/tips/runtime_setData.html)。

### 6.2 页面复杂度预算

- 首屏节点不超过 500；
- 单页总节点不超过 1,200；
- 节点嵌套深度不超过 20；
- 活动列表单页显示 10–20 条；
- 同时保留的高分辨率图片不超过 4 张；
- 只预加载当前屏幕前后 1–2 屏内容。

长列表使用分页和增量追加；离屏高分辨率图片应释放；图片先固定比例；非首屏 Module 延后创建；不参与渲染的大对象不得留在页面数据中；不可见且无交互价值的旧 UI 应从渲染树中删除。

### 6.3 JavaScript 主线程预算

- 单个同步任务不超过 50ms；
- 中端 Android 上，`onLoad` 与 `onShow` 同步任务合计不超过 150ms；
- 启动阶段只同步读取欢迎状态和必要会话状态；
- 不在页面打开时全量扫描历史记录或大型配置；
- 搜索和连续输入使用 200–300ms 防抖；
- 相同读取请求去重；
- 性能日志不得包含身份信息或健康内容。

### 6.4 动画和流畅度

- 主要动画只使用 `transform` 和 `opacity`；
- 不持续动画化 `width`、`height`、`top` 等布局属性；
- 页面和文字过渡时长为 200–350ms；
- 点击反馈在 100ms 内出现；
- 首页文案切换不等待下一张图片网络完成；
- 轮播使用微信原生 swiper 能力；
- 同一全屏页面只运行一个主要过渡动画；
- 新交互发生时取消或合并旧动画，不排队播放；
- 性能优化不得删除已经批准的必要过渡。

滚动期间不得执行图片压缩、大型 JSON 处理或同步存储；报名和提交按钮点击后立即锁定当前动作，只更新按钮与状态区域；已加载 Tab 先展示缓存内容再刷新；键盘弹出和收起不得引起布局持续抖动。

页面跳转和渲染建议参考：[页面切换](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/tips/runtime_nav.html)与[渲染性能](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/tips/runtime_render.html)。

### 6.5 内存预算

- 中端 Android 稳定运行建议值不超过 120MB；
- 峰值不超过 180MB；
- 连续切换四个 Tab 10 轮后，内存增长不超过初始稳定值的 20%，且不得线性增长；
- 连续打开并关闭详情 10 次后，内存回落到初始稳定值的 15% 范围内；
- 完整旅程运行 15 分钟无内存告警、崩溃或持续卡死；
- 页面栈建议不超过 6 层。

页面隐藏或卸载时必须清理计时器、监听器、观察器和已失效请求；进入后台后停止轮播附加计算和持续更新；根据旅程使用 `switchTab`、`redirectTo` 或 `reLaunch`，避免无意义堆栈；收到内存告警时优先释放屏外媒体、临时数据和可重建缓存；不得长期保留图片二进制或重复响应副本。

官方建议参考：[内存优化](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/tips/runtime_memory.html)。

## 7. 各页面性能预算

| 页面 | 性能要求 | 失败或弱网处理 |
| --- | --- | --- |
| 欢迎页 | 首个可理解内容 iOS ≤ 0.9 秒、Android ≤ 1.4 秒；不发起业务数据请求 | 第一屏优先，第二屏延迟加载；高清资源失败时使用轻量回退视觉，不出现白屏 |
| 首页 | 缓存内容 ≤ 300ms；新内容请求 P75 ≤ 600ms；首张主视觉完整显示 iOS ≤ 1.8 秒、Android ≤ 2.5 秒 | 使用最近一次已发布内容；更新失败不阻塞轮播和跳转 |
| 登录页 | 点击反馈 ≤ 100ms；授权状态提示 ≤ 200ms | 微信流程超过 3 秒显示等待说明，超过 15 秒提供重试；按钮不得永久锁死 |
| 注册页 | 输入和选择反馈 ≤ 100ms；提交后 ≤ 200ms 进入处理中状态 | 保留已填写内容；手机号验证失败或网络中断时可重试，避免重复注册 |
| 健康首页 | 游客公共内容 ≤ 1 秒；评测分包首次进入 ≤ 1.5 秒 | 登录后才读取受保护状态；未完成时使用稳定骨架，不显示错误健康结论 |
| 健康问卷 | 下一题切换 ≤ 100ms；填写过程不依赖逐题网络提交 | 本地暂存当前进度，恢复网络后统一提交 |
| 评测提交 | 点击反馈 ≤ 100ms；提交 P75 ≤ 1 秒、P95 ≤ 2 秒 | 超时进入“结果确认中”，查询最终状态，不重复生成记录 |
| 生活方式建议 | 先展示已生成建议；模型生成不得阻塞首次进入 | 使用最近一次有效建议；没有历史建议时给出中性等待说明 |
| 活动列表 | 缓存或骨架 ≤ 300ms；列表和加载更多 P75 ≤ 800ms | 使用最近一次已发布活动；下一页失败不清空当前列表 |
| 活动详情 | 标题和返回导航 ≤ 300ms；首张内容图标准 4G ≤ 1.2 秒、弱网 ≤ 2 秒 | 单图自动重试一次，之后显示固定比例占位和手动重试 |
| 活动报名 | 点击反馈 ≤ 100ms；写入 P75 ≤ 1 秒、P95 ≤ 2 秒 | 超时后查询权威报名状态，不直接提示成功或失败 |
| 我的 | 游客页面 ≤ 500ms；登录资料 P75 ≤ 800ms | 资料失败时保留默认头像、昵称和基础菜单 |
| 我的订单 / 优惠券 | 点击反馈 ≤ 100ms | 跳转期间显示等待；失败时允许重试，不在 myRoot 读取会员资产 |
| 沉浸式图文详情 | 页面框架 ≤ 300ms；首张图标准 4G ≤ 1.2 秒、弱网 ≤ 2 秒 | 分段加载，单张失败不影响其他内容和返回导航 |

微信原生授权、手机号验证弹窗和跳转其他小程序的内部耗时不计入 myRoot 后端响应预算，但必须纳入用户等待、失败、重试和页面可恢复验收。

## 8. 弱网与离线降级

### 8.1 测试网络档位

- 标准 4G：往返延迟约 80ms，下行 10Mbps；
- 弱网：往返延迟约 200ms，下行 1.5Mbps、上行 750Kbps、丢包率 1%；
- 离线：无可用网络；
- Wi-Fi：使用验收现场稳定网络，并记录实际条件。

这些参数用于形成可重复测试条件，不代表所有真实用户网络。

### 8.2 统一降级顺序

1. 展示可信的本地缓存和页面结构；
2. 展示固定尺寸占位或骨架，避免布局跳动；
3. 使用较低分辨率图片；
4. 展示最近一次已发布内容；
5. 给出明确的重试入口和状态说明。

不得降级或伪造：

- 用户身份和手机号验证结果；
- 健康评测结论和风险提示；
- 活动报名最终状态；
- 用户已经提交的数据；
- 已批准高保真图的主要布局和交互关系。

### 8.3 离线和结果未知处理

| 操作类型 | 处理规则 |
| --- | --- |
| 首页、活动等公共读取 | 展示最近一次已发布缓存，并说明内容暂未更新 |
| 登录、手机号验证 | 不伪造成功，提示恢复网络后重试 |
| 健康问卷填写 | 允许继续填写并本地暂存，提交必须联网 |
| 注册、评测提交、报名等写入 | 超时后标记“确认中”，通过权威查询恢复真实状态 |
| 模型生活方式建议 | 使用最近一次有效建议，不生成未经确认的替代结论 |
| 外部小程序跳转 | 保持当前页面可恢复，失败后允许重新发起 |

## 9. 性能监测 Module

### 9.1 Interface 与 Implementation

建立统一的 `Performance Monitoring Module`。它的 Interface 只暴露性能事件记录与候选版本报告能力，不让各页面理解采样、聚合和上报细节。

Implementation 汇总：

- 小程序启动、首屏完成、页面跳转；
- 网络请求、图片加载和分包加载；
- 登录、注册、问卷提交和活动报名等关键操作；
- 卡顿、内存告警、请求失败和结果未知；
- 微信 `wx.getPerformance()`、`PerformanceObserver` 与业务计时数据。

官方能力参考：[Performance](https://developers.weixin.qq.com/miniprogram/dev/api/base/performance/wx.getPerformance.html)与[PerformanceObserver](https://developers.weixin.qq.com/miniprogram/dev/api/base/performance/PerformanceObserver.html)。

不为尚未出现的多个监测平台提前建立 Adapter Seam；只有真实存在第二种 Adapter 时再抽取可替换 Seam，避免首发增加浅 Module。

### 9.2 数据最小化与采样

- 开发版、体验版和候选版本：性能事件 100% 采集；
- 正式环境普通性能事件：默认 10% 采样；
- 崩溃、内存告警、登录失败、注册失败、问卷提交异常和报名结果未知：100% 采集；
- 记录版本、平台、基础库、网络类型、页面、进入方式和代码包状态；
- 不记录手机号、昵称、头像、健康答案、健康结论、活动报名内容或会员资产；
- 性能记录不能成为新的用户画像数据源。

## 10. 真机验收矩阵

每次候选版本至少覆盖：

- iOS 基准设备：较旧但仍处于正式支持范围的 iPhone；
- iOS 主流设备：近两代 iPhone；
- Android 基准设备：4GB 内存中端设备；
- Android 主流设备：8GB 内存中高端设备；
- 项目声明的最低微信基础库版本；
- 验收时的微信稳定版本；
- 本地包启动、首次下载和版本更新；
- Wi-Fi、标准 4G、弱网和离线恢复。

最低微信基础库版本必须在首个开发任务开始前，根据正式上线所需微信能力锁定并写入项目配置；候选版本同时验证该最低版本和验收时稳定版本。设备的品牌、型号、系统版本、微信版本、基础库和网络条件必须随报告留证，不允许只写“iOS 已测”或“Android 已测”。

## 11. 四层发布 Gate

| Gate | 检查内容 | 不通过处理 |
| --- | --- | --- |
| 静态资源 Gate | 主包、分包、图片、字体与单次新增体积 | 超预算不得进入候选版本 |
| 自动化 Gate | 启动、Tab、登录、注册、问卷、活动列表和报名旅程 | 核心旅程失败不得进入真机验收 |
| 真机性能 Gate | 本文件全部启动、页面、交互、流畅度与内存指标 | 任一硬指标失败，候选版本不通过 |
| 产品体验 Gate | 优化后仍符合批准的高保真图和交互 | 不得删除内容或动画伪造达标 |

### 11.1 回归判定

- 超过本文件绝对硬上限：直接阻断；
- 相比最近批准基线退化 5% 以上：预警并分析；
- 退化 10% 以上：即使仍在上限内也阻断；
- 主包或总包单次增长超过 50KB：预警；
- 单次增长超过 100KB：说明原因并重新批准；
- 性能例外必须写明指标、原因、负责人、风险、临时措施和失效版本，不允许永久豁免。

## 12. 正式上线观察标准

上线动作需要单独明确批准，本文件不授权上线。正式发布后的前 72 小时重点观察：

- 启动与页面跳转 P75/P95；
- 崩溃率和内存告警；
- 网络技术错误率；
- 图片加载失败率；
- 登录、注册、问卷提交和活动报名结果未知率。

| 指标 | 警戒线 |
| --- | ---: |
| 崩溃率 | ≥ 0.1% |
| 网络技术错误率 | ≥ 1% |
| 图片加载失败率 | ≥ 1% |
| 写入结果未知率 | ≥ 0.5% |
| 核心页面 P75 退化 | ≥ 10% |
| 登录、注册、评测或报名失败率 | ≥ 2% |

数据错误、用户身份错配或健康结果错配不设置容忍比例。一经发现，停止继续放量并进入修复与权威状态核验流程。生产处理必须遵守独立的发布、回退和流量批准规则。

## 13. 候选版本交付物与责任

每个候选版本必须附带：

1. 包体和资源预算报告；
2. 真机设备与网络矩阵；
3. 各核心旅程 P75、P95 结果；
4. 与上一批准基线的回归比较；
5. 未通过项和性能例外清单；
6. 产品与 UED 一致性确认；
7. 开发、测试、产品和发布负责人的确认记录。

责任划分：

- 开发负责性能预算实现、自动检查、监测 Module 和回归报告；
- 测试负责真机矩阵、网络档位、核心旅程与异常恢复验收；
- 产品与 UED 负责确认优化未损害已批准体验；
- 运营负责上传符合预算的正式素材，不使用后台绕过硬上限；
- 发布负责人负责确认 Gate 证据完整，但无权自行跳过产品、健康安全或数据真实性 Gate。

## 14. 明确不做

- 不优化即将删除的旧任务、打卡、奖励、内部订单和退款链路；
- 不引入第三方重型监测依赖来替代微信原生能力与必要业务计时；
- 不建设实时全量用户追踪系统；
- 不采集个人身份、健康答案或会员资产用于性能分析；
- 不因后台或模型响应慢而阻塞页面首次展示；
- 不以缓存结果伪造注册、评测提交或报名成功；
- 不将候选版本通过等同于微信审核、正式发布或线上稳定。
