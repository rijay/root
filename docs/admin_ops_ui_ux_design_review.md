# ROOT 后台运营工作台 UI/UX 设计评审

版本：V0.1
日期：2026-05-24
评审对象：[admin_ops_ui_ux_design.md](./admin_ops_ui_ux_design.md)
评审结论：有条件通过，进入开发拆单前需修订 P0

## 1. 总体结论

本版设计方向正确，可以作为后台改版的主方案继续推进。

成立点：

- 默认首页从开发校准视角切换为运营工作台，符合小程序运营者日常使用场景。
- 6 个 tab 的信息架构基本清晰，可以把当前后台能力重新归位。
- 手动匹配有赞订单被提升为独立主流程，符合当前上线前真实运营需求。
- ROOT 品牌视觉被控制在后台可用范围内，没有继续沿用大 hero 的低效结构。
- 开发相关能力被收纳到「开发与发布」，不会干扰运营者日常工作。

主要风险：

- 订单匹配流程仍需从“表单录入”收紧为“搜索、预览、确认、写入”的防错流程。
- 今日运营 tab 需要明确哪些数据来自现有后台，哪些需要新增统计。
- 「导入有赞样本」和「真实样本导入」容易让运营者混淆，需要拆清使用场景。
- 部分按钮文案隐含了系统尚不具备的外部联系能力，需要改成可执行动作。

## 2. P0 必须修订

### P0-1 订单匹配需要增加“匹配预览”步骤

问题：

当前设计直接给出手动匹配表单，但运营实际操作时最容易出错的是：订单号已存在、手机号不一致、用户已有活跃订单、订单绑定了其他用户。

修订要求：

订单匹配流程调整为四步：

1. 搜索：输入订单号、收货手机号或用户手机号。
2. 预览：并排展示候选订单、候选用户、匹配风险。
3. 确认：运营选择匹配动作，并填写备注。
4. 写入：成功后展示后续动作。

确认页必须展示：

- 用户昵称、用户手机号、当前状态。
- 有赞订单号、收货手机号、商品、金额、物流状态。
- 风险提示。
- 写入后动作：仅绑定订单 / 生成已送达待开始 / 生成物流异常待办。

验收口径：

- 有风险时不能一键提交，必须二次确认。
- 手机号不一致时必须展示醒目提示。
- 订单已绑定其他用户时默认阻止，除非选择“确认改绑”。

### P0-2 订单匹配要拆成两个模式

问题：

设计里“新建手动订单”和“匹配订单”混在同一个表单里，开发时容易把“创建订单”和“绑定用户”做成一个模糊动作。

修订要求：

订单匹配 tab 拆成两个清晰模式：

- `录入/更新订单`：只负责把有赞订单写入后台，可不绑定用户。
- `匹配给用户`：负责把已有订单绑定到小程序用户。

推荐页面结构：

- 左列：订单搜索与订单详情。
- 中列：用户搜索与用户详情。
- 右列：匹配预览与确认操作。

验收口径：

- 运营可以只录入订单，不强制匹配。
- 运营可以从已有订单选择用户完成匹配。
- 两种模式的成功反馈不同。

### P0-3 今日运营的数据来源需要明确

问题：

设计提出“待匹配订单”“风险用户”等指标，但没有定义它们与当前后台数据的对应关系。

修订要求：

今日运营指标先按现有数据落地：

| 指标 | 数据定义 |
| --- | --- |
| 今日应打卡 | `summary.dueToday` |
| 今日已打卡 | `summary.checkedToday` |
| 今日未打卡 | `summary.missedToday` |
| 待处理任务 | open operation tasks |
| 待匹配订单 | `youzanOrders` 中无 `user_id` 的订单 |
| 待审核免单 | `refundWorkItems` 中 `PENDING` |
| 已送达待开始 | `readyToStartUsers` |
| 异常反馈 | `feedbacks` 中 high severity 或 `FEEDBACK_FOLLOW` 待办 |

验收口径：

- 开发拆单不得发散成新的 BI 体系。
- 首版只使用现有 Dashboard 能返回或轻量扩展的数据。

### P0-4 “导入有赞样本”入口需要重新命名

问题：

订单匹配 tab 中的“导入有赞样本”和开发与发布 tab 中的“真实样本导入”容易混淆。前者是运营动作，后者是 Adapter 校准动作。

修订要求：

订单匹配 tab 中按钮改为：

- `批量粘贴订单`

开发与发布 tab 中保留：

- `真实样本导入`

说明差异：

- `批量粘贴订单`：用于运营临时把有赞订单写入后台并参与匹配。
- `真实样本导入`：用于开发/管理员校准平台字段、状态映射和 Adapter 准入。

验收口径：

- 运营 tab 不出现 Adapter 准入相关解释。
- 开发与发布 tab 保留样本评审和映射能力。

### P0-5 外部联系动作不能暗示系统自动联系用户

问题：

设计中出现 `联系用户`，但当前后台没有企业微信直接发消息能力。如果按钮直接叫“联系用户”，容易让运营误解为系统会自动触达。

修订要求：

按钮改成：

- `复制跟进话术`
- `标记已联系`
- `生成跟进待办`

如后续接企业微信 Adapter，再增加真正的发送能力。

验收口径：

- 首版不承诺自动发送消息。
- 所有跟进动作都能被运营手动完成并标记状态。

## 3. P1 建议修订

### P1-1 补充任务优先级映射

建议把 `task_type` 到优先级、文案、颜色统一定义，否则各列表会出现不一致。

建议映射：

| 任务类型 | 展示文案 | 优先级 |
| --- | --- | --- |
| `FULFILLMENT_EXCEPTION` | 物流异常 | 高 |
| `MANUAL_REVIEW_REQUIRED` | 需要人工确认 | 高 |
| `FEEDBACK_FOLLOW` | 异常反馈跟进 | 高 |
| `REFUND_PENDING` | 免单待审核 | 中高 |
| `DELIVERED_NOT_STARTED` | 已送达待开始 | 中 |
| `MISSED_CHECKIN` | 今日未打卡 | 中 |
| `COUPON_UNUSED` | 优惠券未使用 | 低 |

### P1-2 补充操作确认和备注

以下动作建议必须有确认：

- 审核通过免单。
- 改绑订单。
- 标记物流异常。
- 跳过高优先级待办。

确认弹层建议包含备注字段，方便后续追溯。

### P1-3 后台日期展示也应遵守中文日期规则

后台面向运营，也应避免直接展示 `2026-05-24`。

建议：

- 当前年份展示 `5月24日`。
- 非当前年份展示 `2026年5月24日`。
- 开发与发布 tab 的原始日志可保留内部时间格式。

### P1-4 用户详情抽屉需要固定关键区

用户详情内容很多，建议顶部固定三项：

- 用户当前状态。
- 当前卡点。
- 下一步建议动作。

其他信息再按订单、打卡、反馈、免单分组展开。

## 4. P2 后续优化

- 增加运营视角的快捷筛选保存，例如“我的今日待办”。
- 增加表格横向密度设置：舒适 / 紧凑。
- 增加导出今日待办 CSV。
- 增加后台页面键盘快捷操作，例如刷新和搜索聚焦。
- 后续若接入多运营账号，再补操作人和权限。

## 5. 保留项

以下设计保持不变：

- 6 tab 顶层信息架构。
- 默认进入今日运营。
- 开发相关内容进入「开发与发布」。
- ROOT 暖白、苔绿、墨黑的视觉方向。
- 后台不使用大面积 hero。
- 手动匹配有赞订单作为 P0 主能力。

## 6. 评审结论

结论：有条件通过。

进入开发拆单前必须先修订：

1. 订单匹配四步流程。
2. 订单录入与订单匹配两个模式。
3. 今日运营指标的数据来源。
4. 批量订单导入与开发样本导入的命名区分。
5. 跟进按钮的可执行文案。

修订完成后，可以进入开发拆单。拆单时优先级建议：

1. 后台 tab 架构与视觉底座。
2. 今日运营首页。
3. 订单匹配流程。
4. 用户详情重组。
5. 免单与售后。
6. 开发与发布内容迁移。
