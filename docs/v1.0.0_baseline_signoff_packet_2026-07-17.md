## 2. 签署角色

Baseline 最终接受至少需要独立 Baseline Signoff Contract 中的六类具名角色：

1. `PRODUCT`
2. `OPERATIONS`
3. `ENGINEERING`
4. `QA`
5. `PRIVACY`
6. `HEALTH_CONTENT_REVIEW`

正式姓名、部门和授权依据必须保存在受控审批系统；公开代码仓只保存不可反查的 `signerRef`、`authorityEvidenceRef` 和不可变审批 digest。不得把姓名、部门、签名图片或邮箱写入公开仓库。

职责分离按 decisionId 校验：同一决定下 `PRODUCT` 不得与 `PRIVACY` 或 `HEALTH_CONTENT_REVIEW` 共用 `signerRef`，`ENGINEERING` 不得与 `QA` 共用 `signerRef`。其他一人多角色也必须由组织授权政策允许，并为每个角色独立表态；不得用群聊昵称、`OWNER_TBD` 或“团队已知晓”代替。

### 2.1 签署执行控制面

正式发起 D-001～D-010 前，必须先在受控审批系统登记以下非公开 metadata；任一字段缺失时，状态保持 `BASELINE_OPEN / SIGNOFF_EXECUTION_CONTROL_PENDING`，不能称为“只差签名”：

```text
approvalSystemRef: opaque ref to the controlled system instance
workflowInstanceRef: immutable opaque workflow/run ref
workflowOwnerSignerRef: accountable owner for routing and escalation
evidenceCustodianSignerRef: accountable owner for immutable evidence export
openedAt: ISO-8601 with timezone
dueAt: ISO-8601 with timezone
escalationPolicyRef:
revocationSourceRef:
sourceInputBindingDigest: 8f1147e6efd6dfb0a3d0a9f89143f355042248c09e4d4c4bcb4a91ca53778960
```

`sourceInputBindingDigest` 必须等于本轮冻结 source 的同一绑定摘要；`dueAt` 到期、workflow 被取消、revocation source 不可读或 owner 授权被撤销时，Registry 外层执行流程必须停止收件并回到 `OPEN`。工作流 owner 或证据保管人只有在另有角色授权且提交独立 signoff 记录时，才可计入六类签署覆盖。公开仓只记录上述 opaque ref 与受控导出 digest，不记录人员姓名、邮箱、审批链接或可操作凭据。

## 4. 单个签署记录模板

每位签署人提交一条完整记录：

```text
signoffId: signoff:sha256:<64 hex>
signerRef: actor:sha256:<64 hex>
role: PRODUCT | OPERATIONS | ENGINEERING | QA | PRIVACY | HEALTH_CONTENT_REVIEW
decisionId: D-001 | ... | D-010
decision: APPROVED | REJECTED | APPROVED_WITH_CONDITIONS
conditions:
  - conditionId:
    ownerRef:
    deadline: ISO-8601 UTC with milliseconds
    status: OPEN | CLOSED
    closureEvidenceRef:
inputBindingDigest: 8f1147e6efd6dfb0a3d0a9f89143f355042248c09e4d4c4bcb4a91ca53778960
evidenceRef: evidence:sha256:<64 hex>
signedAt: ISO-8601 UTC with milliseconds
signatureMethod: CONTROLLED_APPROVAL_RECORD_V1 | DETACHED_DIGITAL_SIGNATURE_V1
signedPayloadDigest:
signatureDigest:
validatorRef: validator:sha256:<64 hex>
validationStatus: VALIDATED | INVALID
validationEvidenceRef:
validatedAt: ISO-8601 UTC with milliseconds
revocationStatus: ACTIVE | REVOKED
revocationEvidenceRef: null | evidence:sha256:<64 hex>
```

`authorityEvidenceRef` 是受控审批系统里的前置授权依据，不是 Contract document 字段；它必须与 `evidenceRef` 一起由受控证据索引解析。Contract document 使用 exactFields，禁止把 `authorityEvidenceRef` 或其他个人字段注入签署对象。`evidenceRef` 必须指向不可变审批记录或受控文档节点；该记录内必须能由获授权审核人解析 `signerRef` 对应的真实姓名、职务和授权链。转述、聊天截图散图或本地临时路径不够。`revocationStatus=REVOKED`、缺 `signedPayloadDigest/signatureDigest`、未知签署方法或无法验证 payload 时一律拒绝。


`derivedAllDecisionIdsClosed`、`baselineDigest` 与逐决定 coverage 只能由 Validator 输出，不属于可手填 document。Validator 必须逐个 D-001～D-010 读取本文件第 3 节的必需角色集合，并证明：每个角色都有绑定相同 digest 的有效批准；不存在 `REJECTED`；所有 `APPROVED_WITH_CONDITIONS` 条件已关闭；signoffId/角色/决定 ID 唯一且证据可验证。缺任一角色或条件时派生值必须为 `false`。只有派生值为 `true` 且六类合同角色均有有效签署，Registry 才可封装 Baseline Acceptance Envelope；PRD/Design 不做签后状态回写，Gate tracker 只登记 acceptance 的 opaque evidence ref、`baselineDigest` 与验证结果。本模板当前没有任何签名，不产生研发、Candidate、部署或发布授权。

## 6. 签署、Acceptance 与验证顺序

1. 冻结并复核本包第 1 节的 PRD、Design 与 Gate 决议 digest；从本步起不得修改这三份被签字节。内容变更必须形成新的 source digest 和全新签署轮次，不能覆盖旧快照。
2. 先登记并验证第 2.1 节的受控审批系统实例、workflow owner、证据保管人、截止时间、升级与撤销来源；再收集具名角色和权限依据。公开仓只登记不可反查的 signerRef。
3. 每人针对同一个 `inputBindingDigest` 和决定 ID 签署；D-001～D-010 的决定含义以已冻结 PRD 对应行及本包第 3 节为准，不回写 PRD 17.1A。
4. 对条件签署逐项取得关闭证据；条件状态/关闭证据属于独立 signoff document，不能编辑已签 source bytes。
5. 创建不可变 signoff document，运行独立 `Baseline Signoff Contract` Validator；该合同不得依赖 Candidate、环境或 releaseId，避免以发布证据反向授权基线。
6. Validator 派生 `derivedAllDecisionIdsClosed=true` 后调用 `seal` 生成 Baseline Acceptance Envelope，并再次调用 `verify`；受控 acceptance evidence 必须同时绑定 envelope 的 `baselineDigest`、`inputBindingDigest`、`registry.describe().registryDigest`、Validator Implementation digest 与专向测试 digest，Gate tracker 只登记这些 digest、验证结果及 opaque `acceptanceEvidenceRef`。不得手填 `CLOSED`。
7. 封装前后重新读取三份 source digest，必须仍与第 1 节完全一致；任何漂移都使当前 acceptance 失效并回到第 1 步。不得为了把 PRD 首页状态改为 `BASELINE` 而修改已签文件。
8. 只有 acceptance 验证通过、相关本地检查通过，且 commit、push、PR、远端 CI 各自另获授权后，才可推进受控提交与远端验证；V1-T01 仍须按技术评审另行裁决。

不得倒填日期，不得复制签名，不得把“产品决定冻结”升级为“具名签署完成”。

合同工件：`contracts/baseline-signoff/v1.0.0.json`；Validator Interface：`backend/src/baselineSignoffContractRegistry.js`。本包当前仍为草稿的原因是没有任何真实 signoff/acceptance，而不是合同尚未进入远端。受控签署可以绑定本地审查过的合同、Validator、测试与 source digest；Acceptance 验证通过后才可另行申请 commit。后续远端受保护 SHA 必须保持这些字节完全一致并再次验证 envelope；远端 CI 是独立的同源复核 Gate，不反向成为签署前置，避免形成“必须先 commit 才能签、必须先签才能 commit”的循环。
