# ROOT V0.4.0 运营数据稳定化设计评审

版本：V0.1
日期：2026-05-28
评审对象：[v0.4.0_operational_data_prd.md](./v0.4.0_operational_data_prd.md)
评审结论：有条件通过。方向成立，但进入开发拆单前必须先修订 P0 项。

## 1. 评审标准

本轮评审对象是 V0.4.0 的产品需求、后台运营流程和状态流转规则，不评审视觉稿，也不进入代码实现。

评审维度：

1. 数据稳定性：能否解决云托管重启后用户登录态丢失、后台数据清零的问题。
2. 运营可执行性：运营人员是否能每天完成订单 CSV 和物流 CSV 的上传、预览、确认与异常处理。
3. 状态正确性：订单状态、物流状态、用户打卡资格之间是否有清楚的流转关系。
4. 防错能力：自动匹配、手动修正、状态回退是否有足够的风险提示和审计。
5. 隐私与后台安全：手机号、地址、订单、物流等敏感数据是否有最低保护。
6. 开发可落地性：Module、Interface、Adapter 与现有后台能力是否能顺着当前实现推进。

## 2. 总体判断

V0.4.0 方向正确，应该作为当前小程序进入普通用户使用前的主版本推进。

成立点：

- 把 MySQL 持久化和 session 稳定性放在 P0，抓住了线上登录态和后台数据清零的根因。
- 使用真实有赞订单 CSV 和物流状态 CSV 定义字段和枚举，避免了抽象设计。
- 明确了订单导入、物流导入、用户匹配、送达后打卡资格触发的主流程。
- 状态流转覆盖了用户、订单、物流、用户订单绑定、导入批次五条主线。
- 继续坚持“预览、确认、写入”的运营防错路径，符合此前后台订单匹配的设计方向。

主要风险：

- PRD 当前把后台权限放在 P2，但本版本会导入手机号、地址、订单和物流数据，最低后台访问保护必须前置。
- MySQL 只定义了目标，没有定义从当前 SQLite/memory 数据到 MySQL 的迁移、校验和回滚策略。
- 自动匹配规则里允许“系统明确选择最新有效订单”，对真实运营来说仍然偏冒险。
- 手动修正被放在 P1，但物流已签收、订单关闭、手机号冲突这些 P0 流程一定会立刻需要人工处理。
- CSV 导入的“预览”和“确认”还缺少批次锁定、幂等键和原始文件版本的约束。

## 3. P0 必须修订

### P0-1 后台最低访问保护必须从 P2 前置到 P0

问题：

V0.4.0 会把完整手机号、收货地址、订单号、物流单号和用户状态写入后台。如果 `/admin` 在线上可直接访问，即使没有复杂多角色权限，也存在明显数据泄露风险。

修订要求：

首版不必做复杂权限，但必须提供最低访问保护：

1. 后台 `/admin` 需要一个管理员访问凭证。
2. 所有 admin 写操作需要校验该凭证。
3. 凭证不能写死在前端静态文件中。
4. 未授权访问后台时不返回用户、订单、手机号、地址、raw payload。
5. 发布闸口需要检查生产环境是否启用后台访问保护。

允许的轻量方案：

- 单管理员口令。
- 环境变量配置的 admin token。
- 云托管访问控制或网关层保护。

验收口径：

- 未携带管理员凭证时，线上 `/admin` 不能查看订单和用户数据。
- 上传 CSV、手动修正、导出失败行等写操作都必须通过后台访问校验。

### P0-2 MySQL 迁移需要补“迁移、校验、回滚”三段式

问题：

PRD 已明确生产必须使用 MySQL Store Adapter，但缺少从当前 Store 到 MySQL 的切换策略。直接切换容易出现：旧用户丢失、token 丢失、订单重复、打卡记录断裂、回滚无路径。

修订要求：

MySQL 方案需要补充三段式：

1. 迁移前：
   - 识别当前线上 Store Adapter。
   - 导出现有用户、token、订单、打卡、任务、配置。
   - 建立 MySQL schema 版本。
2. 迁移中：
   - 写入 MySQL 后做记录数校验。
   - 对关键用户抽样校验登录态、打卡记录、订单绑定。
   - 阻止迁移过程中的并发导入或写入，或明确双写策略。
3. 迁移后：
   - 云托管重启验证数据仍在。
   - 保留回滚备份。
   - 发布记录中写明 Store Adapter 已切换为 MySQL。

验收口径：

- 迁移前后用户数、打卡记录数、订单数、任务数可对比。
- 云托管重启后 token 仍可识别。
- 如果 MySQL 初始化失败，生产环境不得静默回退到 memory。

### P0-3 Session Interface 需要定义错误响应和小程序处理契约

问题：

PRD 定义了 `SESSION_EXPIRED`，但还缺少小程序和后端之间的完整错误契约。如果所有失败仍然变成 `cloud.callContainer:fail` 或 `fetch failed`，用户体验和排障都会继续混乱。

修订要求：

Session Module 需要定义统一错误结构：

```json
{
  "ok": false,
  "code": "SESSION_EXPIRED",
  "message": "登录状态已过期，请重新登录",
  "requestId": "..."
}
```

至少覆盖：

| code | 场景 | 小程序动作 |
| --- | --- | --- |
| `SESSION_EXPIRED` | token 过期或不存在 | 清理本地 token，进入登录 |
| `SESSION_INVALID` | token 格式错误或已撤销 | 清理本地 token，进入登录 |
| `AUTH_REQUIRED` | 未携带 token | 进入登录 |
| `CONTAINER_UNAVAILABLE` | 云托管临时不可用 | 展示稍后重试，不清理 token |
| `NETWORK_FAILED` | 网络失败 | 展示网络提示，不清理 token |

验收口径：

- session 失效和网络失败在小程序端提示不同。
- 后端错误响应包含 `requestId`，方便排障。
- 只有明确 session 问题才清理本地 token。

### P0-4 自动匹配不允许默认选择“最新有效订单”

问题：

PRD 当前允许“该手机号只匹配到一个当前有效订单，或系统能明确选择最新有效订单”。真实运营里，同手机号多订单可能代表重复购买、代买、同户家庭、补发、售后换货。默认选最新订单会把打卡资格和免单资格绑定错。

修订要求：

P0 自动匹配条件收紧为：

1. 同手机号只有一个有效订单，才允许自动匹配。
2. 同手机号多个有效订单，一律进入 `MULTIPLE_ORDERS_FOR_PHONE`。
3. 后续如要自动选择最新订单，必须进入 P2，并经过真实运营数据验证。

验收口径：

- 同手机号多有效订单不会自动绑定。
- 冲突队列必须展示这些订单的付款时间、商品、金额、物流状态和当前绑定用户。

### P0-5 手动修正的最小闭环需要前置到 P0

问题：

手动修正当前在 P1，但 CSV 导入第一天就会遇到异常：物流已取消、物流先到订单未到、手机号不一致、订单关闭后用户已登录、系统识别错误。没有最小手动修正闭环，P0 导入流程无法真正上线。

修订要求：

把最小手动修正前置到 P0，只保留必要能力：

1. 修正物流状态。
2. 手动绑定订单与用户。
3. 解绑订单与用户。
4. 标记某条冲突已忽略。
5. 每次修正必须填写原因并写入审计。

复杂能力仍可留在 P1：

- 批量修正。
- 审计筛选。
- 修正模板。
- 多人权限。

验收口径：

- 遇到 `已取消`、手机号不一致、订单缺失时，运营能在后台完成处理。
- 高风险修正有二次确认和审计。

### P0-6 CSV 预览与确认需要增加批次锁定和幂等键

问题：

PRD 已要求“预览、确认、写入”，但还没有规定确认时写入的必须是同一个预览批次。如果用户预览 A 文件后又换了 B 文件，或者重复点击确认，可能导致写入内容和预览不一致。

修订要求：

Csv Import Module 需要补充：

1. 预览成功后生成 `batchId`。
2. 预览结果绑定文件摘要，例如文件名、行数、内容 hash。
3. 确认导入时只能传 `batchId`，不能重新上传一份不同文本直接写入。
4. 同一 `batchId` 只能成功确认一次。
5. 同一订单号、同一物流单号需要按幂等规则更新。
6. 导入失败时保留失败行和原因。

验收口径：

- 重复点击确认不会重复生成订单和待办。
- 预览内容和写入内容一致。
- 可在导入批次里回看这次确认对应的文件摘要。

### P0-7 订单状态和物流状态需要明确来源优先级

问题：

有赞订单 CSV 的 `订单状态=已发货` 与物流 CSV 的 `运输状态=运输中/已签收/已取消` 不是同一层含义。如果直接把订单 CSV 的 `已发货` 作为物流状态来源，容易和后续物流 CSV 冲突。

修订要求：

补充状态来源优先级：

1. 订单有效性以有赞订单 CSV 的 `订单状态` 为主。
2. 物流状态以物流 CSV 的 `运输状态` 为主。
3. 订单 CSV 的 `已发货` 可作为弱物流提示：`fulfillmentStatus = SHIPPED`，但必须标记来源为 `ORDER_CSV_INFERRED`。
4. 物流 CSV 写入后覆盖弱物流提示，来源变为 `FULFILLMENT_CSV`。
5. 手动修正优先级最高，来源为 `MANUAL_CORRECTION`，并保留审计。

验收口径：

- 仅有有赞订单 `已发货` 时，用户只能看到等待送达。
- 物流 CSV `已签收` 写入后才进入 `READY_TO_START`。
- 物流 CSV `已取消` 可以覆盖此前弱物流提示。

### P0-8 raw payload 与隐私展示需要有最低约束

问题：

PRD 要求保留 raw payload 用于追溯，但 raw payload 中包含姓名、手机号、地址等敏感信息。没有保留范围、展示范围和脱敏规则，会让后台安全风险放大。

修订要求：

1. 后台列表默认手机号脱敏。
2. 地址默认不在列表展示，只在详情中展示。
3. raw payload 只在开发与发布或详情调试区展示。
4. raw payload 展示需要管理员凭证。
5. 导入批次保留 raw payload 时要避免前端一次性渲染全部原始行。
6. 导出失败行属于敏感操作，需要后台访问校验。

验收口径：

- 运营列表不会大面积展示完整手机号和地址。
- 未授权访问无法拿到 raw payload。

## 4. P1 建议修订

### P1-1 增加“每日导入顺序”说明

建议在 PRD 中明确推荐顺序：

1. 先上传有赞订单 CSV。
2. 再上传物流状态 CSV。
3. 若物流先上传而订单不存在，生成 `FULFILLMENT_ORDER_MISSING`，后续订单导入后可自动再匹配。

这样可以降低运营每天操作的不确定性。

### P1-2 冲突队列需要支持按类型筛选

建议冲突队列首版就提供基础筛选：

- 全部。
- 手机号多订单。
- 物流找不到订单。
- 手机号不一致。
- 未知状态。
- 已取消或异常。

否则运营会在导入较多数据后难以定位真正要处理的问题。

### P1-3 用户详情需要突出“当前卡点”

用户详情新增订单和物流后，信息会变多。建议顶部固定三项：

- 当前用户状态。
- 当前卡点。
- 下一步建议动作。

示例：

| 状态 | 当前卡点 | 下一步 |
| --- | --- | --- |
| `ORDER_SHIPPED` | 物流运输中 | 等待物流更新 |
| `ORDER_CONFLICT` | 同手机号多个订单 | 运营确认绑定订单 |
| `READY_TO_START` | 已送达未开始 | 提醒用户开始打卡 |

### P1-4 状态映射维护需要区分“建议映射”和“正式映射”

未知枚举映射有风险。建议：

- 系统可以给出建议映射。
- 管理员确认后才成为正式映射。
- 高风险映射到 `DELIVERED` 时必须二次确认。

### P1-5 导入批次详情要提供可操作跳转

导入批次不只是台账，也应该能进入处理动作：

- 点击失败数，进入失败行明细。
- 点击冲突数，进入冲突队列筛选结果。
- 点击已送达待开始数，进入用户列表筛选结果。

## 5. P2 后续优化

以下内容保持 P2 即可：

- 失败行导出。
- 每日运营摘要。
- 用户侧更细的物流公司和运单号展示。
- 多运营账号和角色权限。
- 运营日报和趋势图。

但需要注意：多角色权限是 P2，不代表 V0.4.0 可以没有任何后台访问保护。最低访问保护已提升为 P0。

## 6. 状态流转评审

### 6.1 用户状态

结论：基本成立，需补两个约束。

修订建议：

1. `AUTHENTICATED -> READY_TO_START` 虽然可以由系统一次完成，但实现和审计中必须记录经过的订单与物流依据。
2. `ORDER_EXCEPTION -> READY_TO_START` 只能由手动修正或后续物流更新触发，不能由用户端自行触发。

### 6.2 订单状态

结论：需要补充语义说明。

当前 `PAID` 被用于承接有赞 `已发货`，技术上可沿用现有枚举，但产品语义容易误解。建议在 PRD 中注明：

- `PAID` 在当前系统中代表“有效订单”，不是单纯支付完成。
- 若后续新增 `ACTIVE` 或 `FULFILLED_ORDER`，再做枚举迁移。

### 6.3 物流状态

结论：成立，但必须补来源优先级。

`ORDER_CSV_INFERRED`、`FULFILLMENT_CSV`、`MANUAL_CORRECTION` 三类来源需要进入开发拆单，否则后续排障很难知道某个物流状态是怎么来的。

### 6.4 导入批次状态

结论：成立，需补 `IMPORTED` 终态。

当前状态流转里 `CONFIRMED -> [*]: 全部成功` 对运营台账不够直观。建议新增：

- `IMPORTED`：全部成功。
- `PARTIAL_IMPORTED`：部分成功。
- `FAILED`：全部失败或写入失败。

## 7. Module 与 Interface 评审

### 7.1 Store Module

结论：方向成立，需补迁移 Interface。

建议补充：

- `exportSnapshot()`
- `importSnapshot(snapshot)`
- `validateSnapshot(snapshot)`
- `getStoreHealth()`

这样 MySQL 迁移可以集中在 Store Module 的 Interface 上，而不是散落在脚本和页面里。

### 7.2 Session Module

结论：方向成立，需补错误契约。

Session Module 的 Interface 不只要返回 user，也要返回明确失败原因，供小程序区分 session 过期和网络异常。

### 7.3 Csv Import Module

结论：是本版本最关键的深 Module，必须保持足够深。

它应隐藏这些复杂性：

- 编码识别。
- CSV 解析。
- 字段别名。
- 状态映射。
- 手机号归一化。
- 预览摘要。
- 批次锁定。
- 幂等写入。
- 失败行原因。

调用方只需要理解 `previewImport` 和 `confirmImport` 两个主 Interface。

### 7.4 Order Matching Module

结论：方向成立，但 Interface 需要把“自动匹配”和“冲突处理”拆开。

建议：

- `autoMatchAfterImport(data, batchId, now)`
- `buildConflictQueue(data, filters)`
- `resolveMatchConflict(data, conflictId, decision, now)`

### 7.5 Manual Correction Module

结论：应前置为 P0 最小闭环。

建议首版 Interface 保持窄：

- `previewCorrection(data, input)`
- `applyCorrection(data, input, operatorContext, now)`

审计查询可以放到 P1。

## 8. 开发拆单前置条件

进入开发拆单前，PRD 需要先完成以下修订：

1. 把后台最低访问保护提升为 P0。
2. 补 MySQL 迁移、校验、回滚策略。
3. 补 session 错误响应契约和小程序处理规则。
4. 收紧自动匹配规则：多有效订单一律进入冲突队列。
5. 把最小手动修正闭环提升为 P0。
6. 补 CSV 批次锁定、内容 hash、确认幂等。
7. 补订单/物流状态来源优先级。
8. 补 raw payload 与敏感信息展示约束。

## 9. 评审结论

结论：有条件通过。

本版 PRD 已经抓住 V0.4.0 的主矛盾：先稳住生产数据和登录态，再把订单与物流 CSV 做成可运营的每日流程。状态流转方向成立，开发顺序也基本合理。

但这版会开始处理真实用户的手机号、地址、订单和物流数据，因此不能把后台访问保护、手动修正和迁移策略留到后面。建议下一步先做 P0 修订版 PRD，再进入开发拆单。
