# myRoot v1.0.0 Gate 与文档规范效力决策

日期：2026-07-15  
状态：`DECIDED_FOR_STRUCTURE_REVIEW / NOT_A_RELEASE_APPROVAL`  
适用版本：myRoot 小程序 `v1.0.0`  
代码参考：仓库 `v0.5.13`，`HEAD=d761ae2`；仅证明当前代码基线，不代表生产运行版本

## 1. 决策结论

结构评审可以在本决策回写 PRD 与 `design.md` 后开始；健康内容、隐私履约、活动运营和订阅送达不要求在结构评审前全部关闭。

四类事项必须分成两层判断：

1. **产品决定是否冻结**：范围、Canonical 状态、路由、触发点、失败行为和责任 Module 是否已经明确。
2. **该阶段证据是否关闭**：内容授权、审核、运营 SOP、真实环境配置、运行回执和同源候选证据是否已经取得。

`产品决定已冻结` 不等于 `Implementation 已完成`，更不等于 `候选已证明` 或 `可以发布`。UED 占位页只用于评审结构、信息层级和条件展示，不关闭任何内容、履约、运营或送达 Gate。

## 2. 文档规范效力

“当前是什么”和“v1.0.0 应当是什么”分开判断：

| 判断对象 | 规范来源 | 规则 |
| --- | --- | --- |
| 当前 Implementation | 仓库代码、可重复校验、目标环境只读回执 | 本地代码只证明本地 Implementation；生产状态必须由目标环境读回证明 |
| 法定、平台、隐私与健康安全要求 | 适用规则、正式授权、审批和审核记录 | 优先于全部产品与设计工件；材料缺失时形成 Gate，不推定为通过 |
| v1.0.0 定位、范围、P0/P1/P2、Canonical 状态、Canonical 路由、事实归属、迁移与发布 Gate | [`v1.0.0_product_requirements.md`](./v1.0.0_product_requirements.md) | v1.0.0 的产品规范；冲突必须回写 PRD，不得由调用方自行选择 |
| 品牌 Token、内容语气、信息层级、页面交互与视觉状态映射 | [`design.md`](./design.md) | 只在不改变 PRD 的范围、状态、路由、隐私和验收时生效 |
| 页面结构与条件展示 | Ardot UED | 是评审工件，不产生业务事实、不新增 Canonical 状态、不关闭 Gate |
| PANE 截图、历史 PRD、迁移稿、截图与口头结论 | 研究或历史证据 | 不自动成为 v1.0.0 规范 |

文档状态采用以下语义：

- `review candidate`：可用于结构评审，不授权正式范围承诺或垂直 Build。
- `baseline`：产品范围、Canonical 状态、路由、事实归属与阶段 Gate 已签字并纳入版本控制，可作为 M1 Foundation Build 的规范输入。
- `approved for candidate`：Gate A、B0、C0 已通过，可创建 D0 0% 候选。
- `release ready`：同一 `ROOT_RELEASE_ID` 下 B1、C1、D1 均有证据；文档状态不能替代运行证明。

任何规范变更必须先写入 PRD或被 PRD 链接的决策记录，再同步 `design.md` 与 UED；未同步前以 PRD 为准。

## 3. 阶段 Gate

| 阶段 | 允许发生 | 必须先满足 | 不可据此声称 |
| --- | --- | --- | --- |
| 结构评审 | 评审五 Tab、页面层级、主流程、条件页、空/错/拒绝/撤回/人工路径和占位内容 | 本决策、PRD 与 Design 的规范效力、P0/P1、Canonical 状态和路由一致 | 内容已批准、隐私已履约、活动可运营、消息已送达 |
| M1 Foundation Build | 在隔离/非生产环境实现 Route Registry、v1 Store 映射、事件运输、迁移工具、风险探针与证据结构 | PRD 进入 `baseline`；V1-T01 的输入冻结 | 垂直健康/活动闭环已获准、生产可切换 |
| 垂直 Module Build | 实现已具备完整 Interface、内容/运营输入和受控开关的垂直闭环 | 对应 D/H、内容包、运营 SOP 与 H-04P/C0 等“Implementation 进入条件” | 候选运行已证明、可以发布 |
| D0 候选与 B1/C1 | 用冻结工件和唯一 `ROOT_RELEASE_ID` 取得目标候选环境证据 | Gate A、B0、C0 通过 | 正式发布已批准 |
| D1 与灰度 | 真机 UAT、真实动作/送达、联合回退与签字 | B1、C1、全部同源证明通过 | Gate E 已结束；D1 只授权开始内部灰度 |

因此，原句“正式研发交付仍需关闭健康内容、隐私履约、活动运营、订阅送达等 Gate”统一改为：

> **结构评审不以前述运行 Gate 全部关闭为前提。正式交付按阶段授权：M1 Foundation Build 以规范基线和 V1-T 输入为前提；健康、活动等垂直 Module Build 以对应内容、隐私和运营进入条件为前提；订阅真实送达、H-04R 和 required Adapter 运行证据属于同源候选与发布 Gate，只能在 D0 后关闭。**

## 4. 本轮冻结的产品决定

### 4.1 D-005 首发活动闭环：`PRODUCT_DECISION_FROZEN / BASELINE_SIGNOFF_PENDING`

v1.0.0 P0 固定为：

- 活动列表、详情、场次名额、报名、取消和“我的报名”；
- `approvalMode=AUTO` 可直接 `CONFIRMED`；`approvalMode=MANUAL` 先进入 `PENDING`；
- P0 持久化参与状态仅为 `PENDING / CONFIRMED / REJECTED / CANCELED`；
- 候补、签到、出席、活动后反馈和动态任务编排属于 P1；
- 活动真实内容由运营后台上传，UED 只使用明确标注的占位数据，不把占位内容纳入验收。

D-005 的产品范围已冻结；**活动运营 Gate 仍为 `OPEN`**。进入活动垂直 Build 前至少需要一套首发活动内容包、发布/撤回责任人、容量与并发规则、报名审核时限、取消/场次取消规则、联系人、拍摄与隐私说明、客服口径和一次桌面演练。正式验收必须使用运营后台的真实活动版本，查询成功且确实无内容时才可显示“近期暂无活动”。

### 4.2 D-009 健康适用年龄：`PRODUCT_DECISION_FROZEN / BASELINE_SIGNOFF_PENDING`

v1.0.0 健康旅程只向完成成年资格确认的会员开放，不以保存生日原值代替资格判断。未成年人或无法确认者停止新建健康分类/评测，保留首页、商品、公开活动、非健康任务、会员资料、隐私权利与人工协助。若未来支持未成年人，必须另行设计监护人身份、专门说明、同意/撤回事件与数据权利，不能复用成人流程直接上线。

当前 [`miniprogram/pages/legal/index.js`](../miniprogram/pages/legal/index.js) 仍包含“未满十四周岁经监护人同意可使用”的旧通用口径。它不等于 v1 健康旅程允许未成年人进入；在 PRD 成为 baseline 前，产品、健康审核与隐私负责人必须对该旧文案形成保留、改写或分流决定，Implementation 不得自行解释。

### 4.3 D-010 P0 唯一订阅场景：`PRODUCT_DECISION_FROZEN / BASELINE_SIGNOFF_PENDING`

v1.0.0 P0 只保留一个场景：**用户已开始/参与现有打卡任务后，在任务页主动点击“开启明日提醒”，申请一次次日打卡提醒**。

- 触发点在任务行为之后，不在引导、登录、健康同意或活动浏览时索取；
- 用户拒绝后不自动重弹；
- 页面任务状态始终是事实来源，授权不等于送达；
- 现有 `CHECKIN_REMINDER_NEXT_DAY / v2026-06-28-tpl10850` Implementation 可作为迁移输入；微信模板后台标题“活动提醒”不改变产品场景语义；
- 多场景提醒、活动提醒、偏好、频控和效果编排属于 P1。

D-010 的产品决定已冻结；**订阅送达 Gate 仍为 `OPEN`**。025 的唯一真实请求返回 HTTP 412 并被标记为 `UNKNOWN`，026/027 未执行真实业务 POST；因此当前只能称 `RETEST_ELIGIBLE / DELIVERY_NOT_VERIFIED`。v1.0.0 必须在同一 D0 `ROOT_RELEASE_ID` 下以新授权额度完成一次 `errcode=0` 且真机收到的送达证明，未知结果不重试、不复用额度。

## 6. 对结构评审和 UED 的约束

结构评审应覆盖以下条件页，但页面存在不代表 Gate 已关闭：

1. 健康：未询问、拒绝、撤回、需重新确认、成年资格未知、内容未批准、红旗停止、人工协助、提交失败与安全恢复。
2. 活动：加载、真实业务空、数据源不可用、可报名、审核中、已确认、已拒绝、已满、已取消、报名截止、重复提交和人工协助；签到/反馈只作 P1 参考态。
3. 提醒：可申请、已允许、已拒绝、平台禁用、模板不可用、已排期、发送未知和送达已验证；用户页不把未知写成成功。
4. 隐私：平台隐私授权、健康五态、数据导出/更正/删除请求状态、身份核验、部分完成、逾期与人工申诉。

UED 中活动名称、时间、场地、名额与报名结果均标为“运营占位示例”；正式内容由运营后台上传。UED 不新增健康结论、不展示未经批准的量表题目或确定性建议。

本轮已把 Ardot `fileId=684679021092544` 的 `206:23` 从泛化“活动提醒”改为“明日打卡提醒”，主行动改为“开启明日提醒”；该修改只对齐 D-010 场景，不构成授权、排期或送达证据。

## 8. 已知 Implementation 差距

这些差距不阻塞结构评审，但必须进入后续拆单和验收：

1. v0.5.13 [`Health Consent Implementation`](../backend/src/privacyConsent.js) 只有 `GRANTED / WITHDRAWN`；[`首次“暂不同意”`](../miniprogram/pages/health-consent/index.js) 也写为 `WITHDRAWN`，尚不满足 PRD 五态、revision、并发撤回和完整告知快照。
2. 当前没有完整的 Privacy Rights Module 用户闭环；人工联系入口不能替代访问、更正、导出、删除和处理状态回执。
3. 当前 [`Activity Implementation`](../backend/src/campaign.js) 仍是 Legacy 单活动参与模型，不能表达 v1 场次、容量 reservation、取消和“我的报名”；[`/pages/activity/index`](../miniprogram/pages/activity/index.wxml) 仍是旧 7 日计划页面。
4. 次日打卡提醒本地 Implementation 与专向测试可复用，但 v0.5.13 不是 v1.0.0 同源候选，且当前没有真实送达证明。
