# ROOT 7 日试饮打卡流程更新 PRD

版本：V0.1
日期：2026-05-16
状态：待评审
范围：需求拆解，不包含本轮开发实现

## 1. 决策摘要

本次更新要把当前小程序从“用户进入小程序后完成 7 天打卡”升级为“线下获客、企业微信承接、有赞下单、物流送达、小程序打卡、运营跟进、退款与复购转化”的完整试饮运营流程。

现有小程序已经覆盖登录、画像问卷、活动说明、订单匹配、7 天打卡、免单申请、日常打卡和简单后台。新流程的缺口主要在小程序之外的承接链路：身份识别、收货手机号、有赞订单状态、物流送达、企业微信提醒、Day4/Day8 问卷、Day6 优惠券、每日运营待办和人工退款队列。

本 PRD 的建议是保留当前首页状态机的主干，把新增能力拆成独立 Module，通过清晰 Interface 接入现有打卡流程，避免把所有细节继续塞进 `user.state`。这样能提高 Depth，让一个稳定 Interface 支撑多种运营动作，并把后续变化集中在各自 Module 内，提升 Locality。

## 2. 背景与目标

### 2.1 背景

当前线下试饮活动的真实链路如下：

1. 线下活动通过海报、口头讲解和企业微信二维码获客。
2. 用户扫码添加企业微信。
3. 企业微信自动发送试饮入组规则和有赞店铺小程序码。
4. 用户在有赞完成下单，产生订单号、收货人、收货手机号、地址和物流信息。
5. 运营人工匹配企业微信好友和有赞订单，因为微信授权昵称、有赞下单微信名和消费者实际备注名可能不一致。
6. 运营追踪物流，送达后提醒用户进入打卡小程序开始试饮。
7. 用户连续 7 天完成每日记录。
8. Day4 进行中期问卷，Day8 进行收尾问卷。
9. 后台每天汇总打卡、反馈、断卡、待退款和次日企业微信跟进动作。

### 2.2 本次目标

建立一套可执行的试饮流程产品化方案，让运营从“人工盯流程”变成“后台生成待办，企业微信执行跟进，小程序沉淀数据”。

### 2.3 不做什么

1. 本轮不开发代码。
2. 本轮不接入真实有赞、物流或企业微信开放能力，只定义 Adapter 需要满足的 Interface。
3. 本轮不承诺自动化企业微信外呼或群发，优先支持运营手动执行。
4. 本轮不做复杂健康结论，不输出诊断、治疗或确定功效判断，只做身体记录、趋势和用户反馈整理。

## 3. 成功指标

### 3.1 北极星指标

7 天有效完成率：进入试饮组且物流已送达的用户中，完成 7 天打卡并提交 Day8 收尾问卷的比例。

### 3.2 过程指标

1. 入组到订单匹配率。
2. 订单匹配到物流送达确认率。
3. 物流送达到 Day1 打卡启动率。
4. Day1 到 Day4 留存率。
5. Day4 问卷完成率。
6. Day7 打卡完成率。
7. Day8 收尾问卷完成率。
8. 断卡用户次日召回率。
9. 有反馈用户被运营 follow 的完成率。
10. 待退款队列处理时效。
11. Day6 优惠券领取率和使用率。

## 4. 用户与运营角色

### 4.1 用户角色

种子试饮用户：从线下活动进入，对肠道状态、排便情况、睡眠、皮肤、情绪或日常健康管理有兴趣，愿意完成 7 天试饮记录。

### 4.2 运营角色

企业微信运营：负责加好友、解释规则、人工匹配订单、送达后提醒开始、断卡提醒、反馈 follow、最终退款跟进和复购转化。

### 4.3 后台角色

后台使用者不需要复杂权限分层，默认是 ROOT 运营人员。后续如出现多人协作，再增加操作者记录和权限控制。

## 5. 目标流程

### 5.1 入组前链路

1. 用户在线下活动看到活动海报或听到口头介绍。
2. 用户扫码添加企业微信。
3. 企业微信欢迎语发送：
   - 试饮计划说明。
   - 有赞下单入口。
   - 预计 2 到 3 个工作日送达。
   - 7 天连续打卡和免单权益规则。
   - 补卡与断卡规则。
   - 有疑问可随时联系企业微信。
4. 用户在有赞下单。
5. 运营后台创建或导入候选订单。
6. 运营按收货手机号、收货人、备注和企业微信线索进行匹配。

### 5.2 送达与启动

1. 后台每天追踪订单物流状态。
2. 订单进入已送达后，后台生成企业微信提醒待办。
3. 运营发送小程序打卡入口。
4. 用户打开小程序，授权登录并填写手机号或确认收货手机号。
5. 小程序识别用户阶段：
   - 微信授权信息仅用于登录和基础身份。
   - 收货手机号作为订单、物流和用户匹配的主键候选。
   - 微信昵称不作为强匹配依据。
6. 用户完成入组问卷。
7. 用户确认开始后进入 Day1。

### 5.3 7 天打卡

1. 用户每天完成 30 秒记录。
2. 每日记录包含：
   - 今天是否服用产品。
   - 昨日是否排便。
   - 昨日便型。
   - 今日感受或反馈。
   - 可选图片。
3. 打卡页展示进度条和当前 Day。
4. 打卡成功后展示一句关怀话语或轻量反馈。
5. Day4 触发中期问卷。
6. Day6 触发优惠券提醒或领取入口。
7. Day8 触发收尾问卷。
8. 完成 Day8 后进入待退款队列。

### 5.4 运营闭环

1. 后台每天生成 Summary：
   - 当前在组人数。
   - 今天应打卡人数。
   - 今天已打卡人数。
   - 今天未打卡人数。
   - Day4 问卷待完成人数。
   - Day8 收尾问卷待完成人数。
   - 已完成最终问卷且需要退款人数。
2. 后台生成 To do：
   - 断卡用户提醒。
   - 有文字反馈或图片反馈用户 follow。
   - Day4 问卷异常用户 follow。
   - Day8 完成用户人工退款。
   - Day6 优惠券未领取或已领取未使用用户跟进。
3. 运营在企业微信执行动作后，在后台标记已处理。

## 6. 状态设计

### 6.1 保留现有用户主状态

当前主状态可保留：

1. `GUEST`
2. `UNREGISTERED`
3. `REGISTERED_IDLE`
4. `CHECKIN_ACTIVE`
5. `CHECKIN_COMPLETED`
6. `CHECKIN_FAILED`
7. `DAILY_USER`

### 6.2 新增细分状态不要塞入用户主状态

建议通过独立 Module 记录细分状态：

1. Lead 状态：`ADDED_WECHAT`、`RULE_SENT`、`ORDER_PENDING`、`ORDER_MATCHED`。
2. 物流状态：`NOT_SHIPPED`、`SHIPPED`、`DELIVERED`、`EXCEPTION`。
3. 试饮状态：`NOT_STARTED`、`ACTIVE`、`COMPLETED_7D`、`FAILED`。
4. 问卷状态：`DAY4_PENDING`、`DAY4_DONE`、`DAY8_PENDING`、`DAY8_DONE`。
5. 退款状态：`NOT_ELIGIBLE`、`ELIGIBLE`、`PENDING_MANUAL_REFUND`、`REFUNDED`、`BLOCKED`。
6. 优惠券状态：`NOT_TRIGGERED`、`TRIGGERED`、`CLAIMED`、`USED`、`EXPIRED`。
7. 运营待办状态：`OPEN`、`DONE`、`SKIPPED`、`EXPIRED`。

### 6.3 状态流转验收

1. 没有物流送达记录时，用户可以完成登录和问卷，但不应被默认启动 Day1。
2. 订单送达后，后台应能生成提醒进入小程序的待办。
3. 用户开始 Day1 时必须有明确启动动作。
4. Day4 问卷不应阻塞 Day5 打卡，但应进入运营待办。
5. Day8 收尾问卷应阻塞自动进入退款队列。
6. 断卡超过规则后，用户进入失败或人工处理。

## 7. Module 拆解

### 7.1 身份识别 Module

目标：把微信登录身份、收货手机号、有赞订单和企业微信线索关联到同一个试饮用户。

Interface：

1. `identifyUser(wxOpenId, phone, leadHint)`：返回用户身份、匹配置信度和下一步动作。
2. `bindReceiverPhone(userId, receiverPhone)`：绑定或更新收货手机号。
3. `linkWechatLead(userId, externalContactId, remarkName)`：关联企业微信线索。
4. `getIdentityWarnings(userId)`：返回昵称不一致、手机号冲突、订单被占用等风险。

验收：

1. 微信昵称不同不影响订单匹配。
2. 收货手机号能成为匹配主依据。
3. 同一手机号对应多个订单时，后台提示运营确认。
4. 有赞订单已被其他用户绑定时，不能静默覆盖。

### 7.2 订单与物流 Module

目标：把订单匹配和打卡启动分开。

Interface：

1. `matchOrderByReceiverPhone(userId, phone)`：匹配订单，但不自动启动打卡。
2. `updateOrderFulfillment(orderId, deliveryStatus, trackingInfo)`：更新物流状态。
3. `getReadyToStartUsers(date)`：返回已送达但未启动打卡用户。
4. `confirmReceivedAndStart(userId, orderId)`：用户确认收货后启动 Day1。

Adapter：

1. 有赞订单 Adapter：导入订单号、金额、商品、收货人、收货手机号、地址和订单状态。
2. 物流 Adapter：导入快递公司、运单号、物流节点和签收时间。
3. 人工导入 Adapter：用于初期 CSV 或后台手工录入。

验收：

1. `SHIPPED` 不应自动进入 Day1。
2. `DELIVERED` 后后台生成提醒待办。
3. 用户可在小程序确认已收到货并启动。
4. 未匹配订单的用户可进入人工处理，不直接进入退款资格。

### 7.3 活动说明 Module

目标：让用户在小程序和企业微信中看到一致的规则。

内容要求：

1. 活动标题：以肠为始，ROOT 益生元 7 日身体重启计划。
2. 说明这是一段 7 天产品试饮和身体记录，不承诺治疗效果。
3. 订单预计 2 到 3 个工作日送达。
4. 每天 30 秒记录服用、排便和感受。
5. 连续完成 7 天并提交收尾问卷后进入免单处理。
6. 可补卡，但错过记录超过 3 次则权益失效或进入人工评估。
7. 有疑问联系企业微信。

验收：

1. 小程序活动页、企业微信欢迎语和后台话术口径一致。
2. 不出现治疗承诺或确定功效表述。
3. 用户能在开始前理解打卡、补卡、断卡和退款条件。

### 7.4 种子用户画像 Module

目标：把入组原因和具体痛点转成可运营标签。

问卷建议：

1. 加入本次试饮计划的原因：
   - 觉得自己的肠道有些小问题，需要日常调理改善。
   - 对益生元或肠道健康感兴趣，愿意体验新产品。
   - 想通过 7 天记录观察身体状态。
   - 其他，请填写。
2. 主要希望改善或观察的方向，可多选：
   - 排便困难或排便不规律。
   - 便型偏稀或容易腹泻。
   - 腹胀、肠道敏感或饭后不适。
   - 睡眠、皮肤、情绪等状态波动。
   - 没有明显问题，只想做日常养护。
3. 当前日常便型：布里斯托 1 到 7 型。
4. 当前是否正在使用其他益生菌、益生元或类似产品。
5. 可选自由描述。

数据输出：

1. `seed_user_tags`：运营标签。
2. `pain_points`：具体痛点。
3. `profile_version`：问卷版本。
4. `free_text`：用户原话。

验收：

1. 画像可被后台展示。
2. 标签能进入运营待办筛选。
3. 问卷版本升级不破坏历史记录。

### 7.5 每日打卡 Module

目标：保持 30 秒填写，同时沉淀可分析数据。

每日问题：

1. 今天是否服用 ROOT 益生元口服液？
   - 已完成，打卡成功。
   - 还没有，现在就去。
2. 昨日是否排便？
   - 有。
   - 没有。
3. 如果有排便，选择昨日便型。
4. 今日感受或反馈，自由文本。
5. 可选图片，最多 3 张。

体验要求：

1. 展示 Day1 到 Day7 进度条。
2. 提交成功后展示一句关怀话语。
3. 对未服用用户不计入成功打卡，提醒先完成服用。
4. 保留补卡规则。
5. 支持随时反馈入口，不必须等到每日打卡。

验收：

1. 用户能在 30 秒内完成默认路径。
2. 已打卡后不能重复提交同一天。
3. 补卡规则明确，超出窗口进入人工处理。
4. 反馈文本和图片进入后台待办。

### 7.6 Day4 中期问卷 Module

目标：在试饮中途发现体验问题和潜在流失。

触发：

1. 用户完成 Day4 打卡后弹出。
2. 用户跳过后，首页和后台都显示待完成。
3. 不阻塞 Day5 打卡。

建议问题：

1. 目前是否感觉身体状态有变化？
2. 这几天最明显的感受是什么？
3. 是否遇到服用、排便、口感或坚持上的困难？
4. 是否愿意继续完成剩余 3 天？
5. 是否需要运营联系。

验收：

1. Day4 问卷有独立记录。
2. 未完成会进入运营待办。
3. 有负向反馈或需要联系时生成 follow 待办。

### 7.7 Day8 收尾问卷 Module

目标：把 7 天试饮结果转成退款资格和复购转化输入。

触发：

1. 用户完成 Day7 后，第二天进入 Day8 收尾问卷。
2. Day8 完成后才进入待退款队列。

建议问题：

1. 这 7 天是否按计划完成服用？
2. 排便规律、便型、腹胀、睡眠、皮肤或情绪是否有变化？
3. 哪一天开始感受到变化或没有变化？
4. 是否愿意继续使用或了解复购方案？
5. 对产品、口感、价格、打卡流程的建议。

验收：

1. 完成 7 天但未提交 Day8 时，状态是待收尾问卷，不是待退款。
2. Day8 完成后进入人工退款队列。
3. 愿意复购的用户进入转化待办。

### 7.8 Day6 优惠券 Module

目标：在用户即将完成试饮前测试低打扰转化。

规则：

1. Day6 打卡完成后触发优惠券入口。
2. 用户可领取，但不强制购买。
3. 后台记录领取、使用和过期状态。
4. 企业微信运营只对合适人群低频跟进。

验收：

1. Day6 触发不会干扰打卡主流程。
2. 优惠券状态能在后台看到。
3. 后续可以做对照组：有优惠券提醒 vs 无提醒。

### 7.9 运营待办 Module

目标：让后台每天告诉运营“今天该找谁、为什么找、说什么”。

待办类型：

1. 物流已送达但未启动打卡。
2. 昨日未打卡。
3. 连续两天未打卡。
4. Day4 问卷未完成。
5. Day4 问卷负向反馈。
6. 任意一天有强反馈或图片反馈。
7. Day8 收尾问卷未完成。
8. Day8 完成且待人工退款。
9. Day6 优惠券领取后未使用。
10. 愿意复购用户待跟进。

每条待办字段：

1. 用户。
2. 关联订单。
3. 触发原因。
4. 建议动作。
5. 建议话术。
6. 截止时间。
7. 状态。
8. 操作人。
9. 处理备注。

验收：

1. 后台能按待办类型筛选。
2. 运营能标记完成或跳过。
3. 每天 Summary 能统计待办完成率。

### 7.10 退款 Module

目标：把“完成有效试饮”变成明确的人工退款队列。

退款资格：

1. 订单已匹配。
2. 物流已送达。
3. 完成 Day1 到 Day7 有效打卡。
4. 未超过断卡规则。
5. Day8 收尾问卷已提交。

退款流程：

1. 系统生成待人工退款记录。
2. 运营在有赞或支付后台完成退款。
3. 运营回到后台标记已退款。
4. 用户进入日常打卡或复购承接。

验收：

1. 仅完成 Day7 不自动进入退款。
2. 未匹配订单不能进入正常退款队列，只能进入异常处理。
3. 已退款用户不能重复退款。
4. 退款状态能在用户端和后台看到。

## 8. 页面需求

### 8.1 首页

新增或调整：

1. 未送达：展示“订单处理中，预计 2 到 3 个工作日送达”。
2. 已送达待开始：展示“开始 7 日记录”。
3. Day4 待问卷：展示轻量提醒。
4. Day8 待收尾：展示完成权益前的最后一步。
5. 待退款：展示“已进入人工退款处理”。

### 8.2 活动说明页

新增：

1. 完整活动规则。
2. 免单权益条件。
3. 补卡和断卡规则。
4. 企业微信联系入口。
5. 合规提示：本活动用于产品试饮和身体记录，不替代专业医疗建议。

### 8.3 订单匹配页

调整：

1. 输入下单手机号改为输入或确认收货手机号。
2. 展示订单匹配结果和物流状态。
3. 不再把订单匹配成功等同于开始 Day1。
4. 异常时提示联系企业微信或等待人工匹配。

### 8.4 每日打卡页

## 14. 风险与待确认

### 14.1 需要业务确认

1. 品牌命名最终使用 ROOT 还是 LinkVital。
2. 断卡规则是“超过 3 次失效”还是“达到 3 次失效”。
3. 补卡窗口是否仍然是次日 23:59 前。
4. Day8 是 Day7 后次日触发，还是 Day7 完成后立即可填。
5. 免单是必须 Day8 完成后才处理，还是只要 Day7 完成即可进入初审。
6. Day6 优惠券面额、有效期和适用商品。
7. 企业微信是否先手动执行，还是需要后续真实接入。

### 14.2 产品风险

1. 流程过长可能降低启动率，需要控制用户端步骤。
2. 如果运营待办太多但没有优先级，会变成新的人工负担。
3. 微信昵称、有赞身份和企业微信备注不一致，必须避免自动误匹配。
4. 功效分析只能做趋势和反馈整理，不能做诊断或承诺。

### 14.3 技术风险

1. 当前后端使用内存数据，正式使用前需要持久化数据仓库。
2. 真实有赞、物流和企业微信 Adapter 的可用字段需要确认。
3. 如果把所有新状态放进用户主状态，会让 Interface 变浅，后续维护成本上升。

## 15. Verifier 评审记录

按 Harness 做一次自检：

1. 是否覆盖白板流程：已覆盖线下、企业微信、有赞、物流、小程序、Day4、Day8、Day6、后台 Summary、To do 和退款。
2. 是否避免过度开发：本 PRD 只定义需求和 Interface，不包含代码实现。
3. 是否和现有小程序对齐：保留现有登录、问卷、活动页、打卡、免单和日常打卡主干。
4. 是否有假阳性风险：有。企业微信、有赞和物流真实字段未验证，后续开发前必须确认数据来源。
5. 是否保留架构 Locality：通过独立 Module 分摊新增复杂度，避免把状态全部塞进首页和 `user.state`。
