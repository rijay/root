目标 schema：迁移 `001`～`066`

## 1. 已确认事实

1. 本地一次性 MySQL 8.0.43 已完成 `001`～`066` 的真实引擎验证；这只属于本地证据。
2. 公开生产 `/ready` 在本轮只读检查时仍报告 `005_notification_subscription_grants.sql`。
3. 旧启动路径由运行时 MySQL Adapter 自动执行迁移。`063`～`066` 包含 `CREATE/DROP PROCEDURE`，因此旧路径会要求运行时账号持有 DDL / ROUTINE 权限，违反最小权限，或在发布启动时失败。
4. 本轮已完成 CloudBase CLI 设备登录与只读清点，未执行任何远端修改。
5. 2026-07-20 后续读取 revision 详情时，平台接口把完整 `EnvParams` 返回到工具输出，其中包含秘密值。秘密未被使用或写入仓库，但相关凭据必须按已暴露处理并轮换；在轮换完成前不得把本轮会话记录当作可公开证据。

## 2. 已落实的代码控制

1. 生产运行时必须显式配置 `ROOT_MYSQL_MIGRATION_MODE=verify_only`。
2. 运行时启动只校验 `schema_migrations` 的顺序、数量与 checksum；缺迁移、未知版本、乱序或 checksum 漂移均拒绝启动，不执行 DDL。
3. 运行时 MySQL 账号只允许目标 schema 的 `SELECT, INSERT, UPDATE, DELETE`；`CREATE`、`ALTER` 等迁移权限会被拒绝。
4. 独立迁移命令只读取 `MYROOT_MYSQL_MIGRATION_*` 凭据，与运行时 `MYSQL_*` 凭据分离。
5. `--apply` 同时要求 target、release id、64 位授权摘要和完全匹配的写入确认串；命令输出不包含密码或原始授权账号。

## 3. 必须按顺序执行的远端步骤

### Gate A：只读清点

1. 登录 CloudBase CLI，仅读取环境、CloudRun revision、流量规则、VPC 与环境变量名（不输出秘密值）。
2. 确认 Candidate 是否为独立 CloudBase 环境、独立 schema，还是生产环境中的 0% revision。
3. 用运行时账号执行现有只读 preflight；记录迁移版本、`CURRENT_USER()` 的不透明引用、权限、连接容量和 artifact/release id。
4. 用独立迁移账号执行：

```bash
node backend/scripts/mysql-production-migrate.js \
  --plan \
  --target candidate \
  --release-id <candidate-release-id>
```

### Gate B：Candidate 写入

前提：备份/快照可恢复、Candidate 目标已确认、迁移账号与运行时账号分离、授权摘要已签发。

```bash
export MYROOT_MYSQL_MIGRATION_WRITE_CONFIRM='APPLY:candidate:<release-id>:<authorization-sha256>'
node backend/scripts/mysql-production-migrate.js \
  --apply \
  --target candidate \
  --release-id <release-id> \
  --authorization <authorization-sha256>
```

随后部署 0% Candidate，设置 `ROOT_MYSQL_MIGRATION_MODE=verify_only`，运行 `/ready`、只读 preflight、容量实证、跨实例幂等与功能回归。若 Candidate 与生产共用 schema，此步骤本质上是生产 DDL，必须按 Gate C 授权处理，不能以“0% 流量”降低风险等级。

B 方案虽不修改生产 schema，但会修改同一个生产 MySQL 集群的账号目录、容量与备份状态，因此仍按生产变更管理。Candidate 创建、账号创建、迁移、revision 部署与秘密轮换必须分别获得明确授权；选择方案本身不等于写入授权。

### Gate C：生产写入

1. 冻结写入窗口或确认迁移对在线写入的兼容策略。
2. 生成迁移前快照并完成可恢复性校验；记录恢复点引用。
3. 确认迁移 `006`～`066` 的执行窗口、最长锁等待、终止条件和负责人。
4. 使用生产 target 的独立授权串执行同一迁移命令。
5. 迁移完成后部署 `verify_only` revision，再将运行时账号权限收敛为四项 DML 权限。
6. 先做 0%/定向验证，再逐级放量；每级验证 `/ready` 的 `migrationVersion=066_v1_runtime_alert_delivery_severity_slo_authority.sql`、容量与关键业务写入。

## 4. 失败与回滚

1. checksum、顺序、未知版本或结构漂移：立即停止，不自动修复 ledger。
2. DDL 执行错误：停止后续迁移，保留现场；MySQL DDL 可能隐式提交，不能假设事务整体回滚。
3. Candidate 启动报 `MYSQL_MIGRATION_REQUIRED`：保持 0% 流量，先完成迁移，不得切回运行时自动迁移。
4. 权限报 `MYSQL_PRIVILEGE_POLICY_BLOCKED`：核对运行时账号；不得临时给运行时账号加 ROUTINE/DDL 权限。
5. 生产回滚以迁移前恢复点和兼容 revision 为准。若 006～066 含不可逆数据变换，必须先在 Candidate 证明恢复演练；仅回滚代码 revision 不等于回滚 schema。
