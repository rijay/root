# ROOT 打卡小程序 V0.3.0 产品需求设计

版本：V0.1
日期：2026-05-24
状态：产品需求设计
范围：小程序端体验与展示规则；必要时补充轻量后端记录能力

## 1. Harness

目标：把 V0.2.0 的 ROOT 品牌化打卡体验推进到“7 天试饮后可长期日常记录、可分享、表达更自然”的下一版本。

本轮产物：

- V0.3.0 产品需求设计。
- 需求验收标准。
- 后续开发拆单输入。

验收标准：

- 7 天试饮阶段和长期日常记录阶段的叙事清楚分离。
- 分享图需求不承诺直接发布到朋友圈或小红书，只保证生成、预览、保存和可分享素材。
- 日期展示统一为中文自然日期，内部数据存储格式不被 UI 需求误伤。
- 今日打卡页能降低填写阻力，并保留现有必填校验。
- 身体反馈画像只展示用户提交的三个核心字段：参与原因、肠道状态、改善方式。

误判风险：

- 只把文案中的“7 天”删掉，但状态、入口和进度仍在强化 7 天。
- 把分享图做成运营海报，而不是用户每日记录后的个人分享素材。
- 为了日期展示改动后端存储，导致排序、补卡、审计和测试受影响。
- 打卡页视觉变好但填写路径变长。

## 2. 背景

V0.2.0 已完成 ROOT 品牌化 UI、微信规范约束下的首页/打卡/我的页优化，以及基础发布提交。当前体验仍以“7 天身体重启计划”为核心叙事，这对试饮期是成立的，但用户完成 7 天后继续每天打卡时，继续全局强调“7 天”会造成三个问题：

- 用户感觉自己仍停留在试饮任务中，而不是进入日常健康记录。
- 首页、我的页、结果页、历史页中同时出现“累计打卡”和“7 天记录”，阶段感混乱。
- 分享图如果继续围绕 7 天，会弱化日常坚持与身体反馈的长期价值。

本版本的产品目标是：保留 7 天试饮的权益和规则能力，但在完成后把用户体验切换为“日常身体记录”。

## 3. 用户目标与业务目标

### 3.1 用户目标

- 试饮期用户知道自己现在第几天、今天要做什么、完成后下一步是什么。
- 完成 7 天后的用户每天打开小程序时，看到的是“今天的身体记录”，而不是“继续 7 天任务”。
- 用户完成每日记录后，可以得到一张好看、克制、适合朋友圈和小红书发布的分享图。
- 用户查看身体反馈画像时，能直接看到自己提交过的核心内容，而不是抽象标签或不必要字段。

### 3.2 业务目标

- 提高 7 天完成后的日常打卡留存。
- 提高用户主动分享率，为 ROOT 形成自然口碑传播。
- 降低运营解释成本：试饮权益归试饮，长期记录归长期关系。
- 提升顾问查看用户画像时的有效信息密度。

## 4. 版本范围

### 4.1 本版本做

1. 完成后日常打卡阶段的全局叙事调整。
2. 每日打卡完成后的分享图生成与预览入口。
3. 全局中文日期展示格式统一。
4. 今日打卡页信息结构与交互体验优化。
5. 身体反馈画像字段展示优化。

### 4.2 本版本不做

1. 不改变 7 天试饮权益、断卡、Day4/Day8、免单、复购礼的业务规则。
2. 不改动后端内部日期存储格式，仍保留 `YYYY-MM-DD` 作为数据和排序格式。
3. 不做自动发布朋友圈或小红书。
4. 不新增复杂运营后台能力。
5. 不输出诊断、治疗、确定功效或医疗建议。

## 5. 核心状态与叙事规则

### 5.1 阶段定义

| 阶段 | 用户状态 | 主叙事 | 是否强调 7 天 |
| --- | --- | --- | --- |
| 试饮前 | `GUEST` / `UNREGISTERED` / `REGISTERED_IDLE` | ROOT 7 日身体重启计划 | 是 |
| 试饮中 | `CHECKIN_ACTIVE` | 第 N 天身体记录 | 是 |
| 试饮完成待动作 | `CHECKIN_COMPLETED` | 完成试饮记录，处理收尾动作 | 局部保留 |
| 日常记录 | `DAILY_USER` | 今日身体记录 / 日常身体反馈 | 否 |
| 人工协助 | `CHECKIN_FAILED` 或人工确认状态 | ROOT 顾问协助 | 只在规则说明中保留 |

### 5.2 全局表达原则

- 试饮中可以出现“第 N 天 / 7”“7 天进度”“收尾问卷”“免单规则”。
- 进入日常记录后，首页、我的页、每日打卡页、分享图不再以“7 天”为主表达。
- 历史记录可保留“试饮记录”分组，但菜单文案不再叫“7 天记录”，建议改为“记录历史”。
- 完成态可以提示“已完成试饮记录”，但主行动应是“继续日常记录”或“完成收尾问卷”，不是“再看 7 天”。

## 6. 需求明细

### PRD-1001 完成 7 天后进入日常记录叙事

优先级：P0

目标：

- 用户完成 7 天后继续打卡时，全局不再强调“7 天”概念。
- 保留试饮期权益路径，但不让它压过日常记录主路径。

涉及页面：

- 首页 `pages/home/index`
- 今日打卡 `subpkg/checkin/pages/today/index`
- 结果页 `subpkg/checkin/pages/result/index`
- 我的页 `pages/profile/index`
- 记录历史 `subpkg/checkin/pages/history/index`
- 免单申请 `subpkg/refund/pages/apply/index`

产品规则：

1. `CHECKIN_ACTIVE` 保持试饮期进度表达。
2. `CHECKIN_COMPLETED` 若 Day8 未完成，主行动是“完成收尾问卷”。
3. `CHECKIN_COMPLETED` 若 Day8 已完成，主行动是“继续日常记录”，免单状态作为次级信息。
4. `DAILY_USER` 首页主标题使用“今日身体记录”或“今天也记录身体反馈”。
5. `DAILY_USER` 统计字段使用：
   - 累计记录
   - 当前连续
   - 最长连续
6. `DAILY_USER` 不展示“Day N / 7”“完成 N/7”“7 天数据总结”。
7. 我的页菜单中“7 天记录”改为“记录历史”。
8. `CHECKIN_COMPLETED` 和 `DAILY_USER` 状态徽章分别建议：
   - `CHECKIN_COMPLETED`：试饮记录已完成
   - `DAILY_USER`：日常记录中

验收标准：

- 日常记录态页面中不出现“第 N 天 / 7”“N/7”“7 天数据总结”作为主信息。
- 试饮期页面仍能看到 7 天进度，不影响 Day4/Day8/Day6/免单路径。
- 用户从完成态点击继续打卡后，首页刷新为日常记录叙事。

### PRD-2001 每日打卡后生成分享图

优先级：P0

目标：

- 用户完成每日打卡后可以生成一张个人记录分享图，用于保存到相册，再发布到朋友圈或小红书。
- 分享图强调“今日记录”和“坚持”，不承诺产品功效。

触发时机：

1. 用户提交试饮期每日打卡成功后，结果页展示“生成今日分享图”。
2. 用户提交日常打卡成功后，结果页或成功弹层展示“生成今日分享图”。
3. 用户已经完成今日记录后，从首页“查看今日记录”进入历史详情时，也可补生成当天分享图。

分享图规格：

| 项目 | 要求 |
| --- | --- |
| 默认比例 | 3:4 竖版，适合小红书与朋友圈图片流 |
| 建议尺寸 | 1080 x 1440 |
| 视觉 | ROOT 暖白背景、墨黑 logo、苔绿点缀 |
| 内容密度 | 少文字、大留白、可读性优先 |
| 隐私 | 默认不展示手机号；昵称可隐藏或只展示“ROOT 用户” |

分享图内容：

1. ROOT 横版 logo。
2. 日期：例如“5月26日”；非对应年份展示“2026年5月26日”。
3. 主标题：
   - 试饮期：`第 N 天，身体记录已完成`
   - 日常期：`今天，身体记录已完成`
4. 记录摘要：
   - 今日是否服用 ROOT。
   - 昨日是否排便。
   - 若有排便，展示便型中文标签。
   - 用户填写的身体感受，最多展示 40 个字。
5. 坚持信息：
   - 试饮期：`已完成 N 天试饮记录`
   - 日常期：`累计记录 N 天 / 当前连续 N 天`
6. 品牌尾句：
   - `身体自有其序，记录会让它被看见。`
7. 可选小程序码或品牌识别区：
   - 内测期可先使用 ROOT logo 和品牌语。
   - 上线传播前再接入真实小程序码。

分享图动作：

1. 生成中：展示加载状态，避免重复点击。
2. 生成成功：进入预览页或底部弹层。
3. 用户可选择：
   - 保存到相册。
   - 调起微信图片分享能力。
   - 返回首页。
4. 若保存失败，提示用户开启相册权限。
5. 小红书发布不做自动跳转承诺，文案提示“保存后可发布到小红书”。

合规与文案限制：

- 不写“改善便秘”“治好腹泻”“睡眠变好”等确定功效。
- 不展示用户敏感身份信息。
- 不展示订单号、手机号、地址。
- 用户反馈如果过长，截断后加省略号。

验收标准：

- 完成一次打卡后，用户能生成图片并看到预览。
- 图片保存到相册成功后，系统有明确反馈。
- 分享图在试饮期和日常期文案不同。
- 没有手机号、订单号、地址等隐私信息。

### PRD-3001 全局日期展示格式优化

优先级：P0

目标：

- 所有面向用户的日期从 `2026-05-26` 改为中文自然日期；对应年份内展示 `5月26日`，非对应年份展示 `2026年5月26日`。
- 内部数据、排序和请求参数继续使用稳定日期格式。

产品规则：

1. 用户可见日期统一使用中文自然日期。
2. 日期区间格式：
   - 对应年份内：`5月20日 至 5月26日`
   - 非对应年份：`2026年5月20日 至 2026年5月26日`
3. 今天、昨天等相对表达可以保留，但需要搭配绝对日期：
   - 对应年份内：`今天 · 5月26日`
   - 非对应年份：`昨天 · 2025年12月31日`
4. 后台或调试信息可保留内部格式，但用户端小程序页面不得直接展示 `YYYY-MM-DD`。
5. 时间戳如 `2026-05-26T10:30:00+08:00` 不直接展示给用户。

建议 Module：

- `Date Display Module`

Interface：

1. `formatDateCn(dateText, options)`：对应年份内 `2026-05-26` -> `5月26日`，非对应年份 -> `2026年5月26日`
2. `formatDateRangeCn(startDate, endDate, options)`：输出中文日期区间。
3. `formatRelativeDateCn(dateText, todayText)`：输出“今天 / 昨天 / 5月24日 / 2025年12月31日”等展示文案。

验收标准：

- 首页进度、历史记录、详情页、免单周期、订单物流、分享图全部展示中文日期。
- 自动化校验能扫描小程序 WXML 和 JS 中面向用户的日期展示路径。
- 后端测试不因内部日期格式改变而回退。

### PRD-4001 今日打卡页面体验优化

优先级：P0

目标：

- 减少用户填写阻力，让打卡页更像“1 分钟身体记录”，而不是问卷。
- 保留当前数据结构：服用、排便、便型、身体感受、可选图片。

页面结构：

1. 顶部状态区：
   - 试饮期：`第 N 天身体记录`
   - 日常期：`今日身体记录`
   - 说明文案：`按真实情况记录即可，不需要写得完美。`
2. 必填问题区：
   - 今日是否服用 ROOT。
   - 昨日是否排便。
   - 昨日便型，仅在选择“有排便”后展开。
3. 身体感受区：
   - 输入框标题：`今天身体有什么变化？`
   - 占位文案：`例如：腹胀减少、睡得更稳、暂时没有明显变化`
   - 可提供快捷短句，但不能替代用户输入：
     - `暂无明显变化`
     - `腹部更轻松`
     - `排便更顺畅`
     - `睡眠更稳定`
4. 图片上传区：
   - 收起为次级入口。
   - 展示已选择张数。
5. 底部固定行动：
   - 主按钮：`保存今日记录`
   - 未满足必填时，按钮禁用并展示缺失提示。

交互规则：

1. 选择“未服用”仍允许提交，但后端若拒绝，需要展示明确原因。
2. 选择“没有排便”时，不要求便型。
3. 选择“有排便”时，必须选择便型。
4. 文字反馈可选，但应鼓励用户填写真实感受。
5. 提交成功后进入结果页，不只用 toast 后直接回首页。
6. 结果页提供“生成分享图”和“返回首页”。

体验验收：

- 首屏能看到至少两个核心问题和主按钮方向。
- 单手操作时，底部按钮不被安全区遮挡。
- 用户未完成必填项时知道缺哪一项。
- 试饮期和日常期使用不同顶部文案。
- 页面中不出现医疗诊断式反馈。

### PRD-5001 身体反馈画像字段优化

优先级：P1

目标：

- 身体反馈画像页直接展示用户提交内容，减少解释成本。
- 去除“日常便型状态”字段。

当前问题：

- 当前页面已经有“参与原因、肠道状态、改善方式、日常便型”四行。
- 新版本只保留前三项，并优先展示用户选择项对应的中文文案。

展示字段：

1. 参与原因：展示 `join_reasons` 对应中文文案，多选用顿号分隔。
2. 肠道状态：展示 `gut_health_status` 对应中文文案。
3. 改善方式：展示 `improvement_methods` 对应中文文案，多选用顿号分隔。

展示规则：

- 不展示字段 key 或枚举值。
- 字段为空时展示“暂未填写”。
- 多选字段按用户提交顺序或选项定义顺序展示，保持稳定。
- 不再展示 `stool_type`。

验收标准：

- 身体反馈画像页只有三组核心内容。
- 三组内容均为用户提交内容的中文表达。
- 无画像数据时仍显示空态。
- 不再出现“日常便型”行。

## 7. 信息架构调整

### 首页

试饮中：

- 主卡：第 N 天身体记录。
- 进度：N/7。
- 主行动：开始今日打卡 / 查看今日记录。

完成后：

- 主卡：今日身体记录。
- 统计：累计记录、当前连续、最长连续。
- 主行动：今日打卡 / 查看今日记录。
- 次级：试饮记录、免单状态、复购入口。

### 今日打卡页

- 从“第 N 天”表单变为“阶段感知表单”。
- `mode === "daily"` 时不使用“第 N 天”作为主标题。

### 结果页

- 试饮期结果：显示阶段进度和下一步。
- 日常期结果：显示今日记录摘要、连续记录信息、分享图入口。

### 我的页

- 状态徽章跟随阶段变化。
- “7 天记录”菜单改为“记录历史”。
- 身体反馈画像按三字段展示。

## 8. 数据与 Interface 建议

### 8.1 Date Display Module

定位：用户端展示适配，不改变后端内部日期。

Interface：

- `formatDateCn(dateText)`
- `formatDateRangeCn(startDate, endDate)`
- `formatRelativeDateCn(dateText, todayText)`

### 8.2 Share Poster Module

定位：从记录数据生成分享图素材。

Interface：

- `buildSharePosterPayload(record, context)`：生成分享图所需文本、日期、阶段、统计数据。
- `renderSharePoster(payload)`：在小程序端绘制图片并返回临时文件路径。
- `saveSharePoster(tempFilePath)`：保存到相册。
- `recordShareIntent(recordId, channelHint)`：记录用户点击保存或分享的意图。

Adapter：

- Canvas Adapter：小程序端绘制分享图。
- Telemetry Adapter：记录分享图生成、保存、分享入口点击。

说明：

- 如果第一期只做本地生成，可以先不新增后端记录。
- 如果要统计分享转化，建议增加轻量事件记录，复用现有 `event/track` 思路。

### 8.3 Checkin Presenter Module

定位：把 `CHECKIN_ACTIVE`、`CHECKIN_COMPLETED`、`DAILY_USER` 的页面文案和行动集中起来，减少页面里散落判断。

Interface：

- `getCheckinPageCopy(userState, session, dailyStats)`
- `getResultPageCopy(userState, submitResult, session, dailyStats)`
- `getPrimaryAction(userState, session, dailyStats)`

验收：

- 删除这个 Module 后，阶段判断会重新散落到首页、今日打卡页、结果页和我的页，说明它有足够 Depth。
- 页面只消费展示结果，不重复拼接“第 N 天 / 7”和日常状态文案。
