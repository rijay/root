### 6.1 Runtime Alert 数据库写 authority

迁移 061 的 CHECK 只证明单行“当前形状”合法，不证明合法迁移历史，也不冻结 `registration_mode`。迁移 063～065 已将 alert delivery 与 Control Ledger 写路径收敛到 22 个窄 `SQL SECURITY DEFINER` 过程；注册过程返回一行持久化结果，Registrar 无需基表读取。MySQL Adapter 严格解析单一业务结果集的 `CALL`，本地 grant policy 拒绝多余、跨 schema、全局、`GRANT OPTION` 和直接 DML 权限。独立 pool/connection-authority 的本地装配 Interface 与一次性 principal/bootstrap harness 已实现并通过静态测试，但仍未进入真实 MySQL：migration 必须由未来的专用 definer 主体执行，完成后撤销迁移权限、仅保留 22 个过程及必要基表实现权限并锁定账号。真实 principals、grants、真实 pool 凭据注入和 Candidate attestation 尚未发生。因此告警相关关闭条件仍必须拆成：

1. `DB_WRITE_AUTHORITY`：数据库 principal、受控写 Interface、最小 grants、撤销和轮换；
2. `ALERT_RECEIVER_DELIVERY`：真实 receiver、warning/critical 合成投递、ACK、重试与 dead-letter。

两项互不替代。推荐最小 principal 模型：

| Principal | 允许 | 必须拒绝 |
| --- | --- | --- |
| Migration Creator / Procedure Definer（同一主体） | 发布窗口执行 migration；完成后撤销迁移权限，仅保留 22 个过程 `EXECUTE` 与过程 Implementation 所需的 alert/authority/delivery/control-ledger 精确基表权限，并 `ACCOUNT LOCK` | 锁定后登录、作为应用凭据、继续执行 DDL、DELETE、访问额外 schema、`GRANT OPTION`、业务发送 |
| REGISTRAR | 仅 `EXECUTE` 固定模式的注册过程 | 所有基表 SELECT/DML、任意 DDL、DRY_RUN 主体注册 CONTROLLED |
| WORKER | 九个 worker procedure `EXECUTE` + alert/delivery 表 `SELECT`（仅 due/stale locking 与状态读回） | 注册、INSERT/DELETE/DDL、直接生命周期 UPDATE |
| INSPECTOR | inspect procedure `EXECUTE` | 基表 SELECT/DML、worker procedure |

列级 UPDATE 不能阻止形状合法的越级状态写入、覆盖终态或绕过 owner/generation fence，不能单独关闭 Gate。正式模型要求独立 principal 与 `SQL SECURITY DEFINER` 窄过程；不可变列/状态迁移 trigger 只能作为纵深防御。任何 definer 必须不可登录，运行主体不得拥有 global、额外 schema、DDL、DELETE、直接基表 DML 或 `GRANT OPTION`。

Candidate 最小证据：同一 `releaseId` 的 opaque principal refs、脱敏 `SHOW GRANTS` 摘要、procedure/trigger/definer/schema digest、正向过程调用、禁止 INSERT/UPDATE/DELETE/ALTER/DROP 和越级迁移的负向实证、凭据轮换与旧 principal 撤销。当前状态固定为：

## 7. 密钥轮换与保留

当前真实轮换保持禁止。本地 Implementation 已补齐 Command Result 历史密文与 Command Request Digest 历史幂等记录的有界 previous-key 兼容：新写只用 current key，读取/验证按持久 `keyId` 选择 previous key，unknown/retired fail-close；通知 provider receipt 另使用独立 HMAC key id，但当前不提供 previous-key keyring。这不等于 Candidate 已注入、旧记录已全量验证或真实轮换获批。

安全顺序：

1. 本地 current-key 单写、previous-key 按 keyId 读/验、unknown/retired fail-close 已完成并有正反向测试。
2. Key Inventory 已纳入 `REQUEST_DIGEST / COMMAND_RESULT / INBOX_CONTENT / NOTIFICATION_RECEIPT` 四域，退休声明必须是精确 JSON：`{"REQUEST_DIGEST":[],"COMMAND_RESULT":[],"INBOX_CONTENT":[],"NOTIFICATION_RECEIPT":[]}`。REQUEST_DIGEST 同时覆盖 command idempotency、task event、UnionID provenance 与 legacy/v1 recipient binding；NOTIFICATION_RECEIPT 覆盖 send attempt/transition 的 provider receipt digest metadata。报告只含受信 key ID、状态、计数和 unknown 短指纹；请求原文与 provider receipt 原文均不持久化，因此这两类只核验 scheme/digest shape/key reference，legacy `sha256:v0` 仅作 metadata 可见警告，不伪称离线 HMAC 内容复验。
3. Security owner 提供 metadata：key id/version/owner/created/expires/retention，不提供材料。
4. Candidate metadata-only inventory、历史解密/验签、双读单写证明。
5. 明确 rekey/tombstone/TTL、break-glass owner 和回退保留期，并逐域填写以下 metadata：

```text
domain: REQUEST_DIGEST | COMMAND_RESULT | INBOX_CONTENT | NOTIFICATION_RECEIPT

tombstoneTtlDays:
backupRestoreWindowDays:
legalHoldWindowDays:
deploymentPropagationHours:

```

逐域验收不变量：

- `rotationOverlapHours >= deploymentPropagationHours + maximumRetryWindowHours + ceil(clockSkewSafetyMinutes / 60)`。
- `keyMaterialRetainUntil >= max(latestCiphertextCreatedAt + max(recordTtlDays, tombstoneTtlDays, legalHoldWindowDays), lastBackupContainingKeyExpiresAt) + rollbackSafetyWindowDays`。
- 旧 key 只有在 `liveReferenceCount=0` 且 `restorableBackupReferenceCount=0` 后才可申请退休；若备份仍可恢复出旧密文，必须保留解密/验签材料或先完成受控 rekey。
- Key material 保留不等于业务数据可无限保留；数据删除、法定保留、备份到期与密钥销毁分别受隐私批准约束。
- 对 `REQUEST_DIGEST` 与 `NOTIFICATION_RECEIPT`，`latestCiphertextCreatedAt` 应解释为该 keyed digest 的最新持久记录时间；不得因字段名沿用而声称存在可离线认证的原始 request/receipt 内容。
- `NOTIFICATION_RECEIPT` 当前没有 previous-key keyring；旧 receipt key 一旦进入 retired/unknown，而持久引用仍未归零，readiness 必须持续阻断。正式轮换前必须先证明引用归零，或另行评审并实现有界验证 keyring，不得直接替换 current key 后宣称完成轮换。
6. 证明退休 key 引用为 0 后，才可单独授权退休；删除再单独授权。

创建、注入、轮换、批量 rekey、退休和删除是六类不同写动作，不得合并授权。
