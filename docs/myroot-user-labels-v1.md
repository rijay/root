# myRoot 用户标签第一版

本地实现日期：2026-09-04。生产部署日期：2026-09-05。分支：`codex/myroot-user-labels-20260904`；实现提交：`dcd5726`。

本版已部署后台用户标签、来源映射、飞书差异预览及同步恢复逻辑。生产服务 `myroot-api-076` 已承接 100% 流量，迁移 `075_user_labels.sql` 已应用；`myroot-api-075` 保留为回滚版本。云端没有飞书访问凭据，`ROOT_LABEL_FEISHU_WRITE_ENABLED=false`，未向真实飞书表写入用户记录。

## 运营操作

1. 打开「渠道码与漏斗 → 用户来源映射」，选择渠道码或某一配置版本的自报来源，填写活动、城市、合作方、渠道类型和配置依据。
2. 首次配置可填实际活动开始时间，用于历史回填。同一来源的后续版本须选择未来生效时间；已经发生的访问继续使用当时的版本。历史自报来源的选项 ID、名称和版本取自实际保存的确认记录。
3. 打开「用户标签」，按完整 UID 或来源状态查询。来源冲突显示待核验；没有可靠访问证据时首次访问留空。注册时间不代替访问时间。
4. 有个人健康标签权限的管理员可勾选「查看测评信息」，在详情中查看基准测评、题目版本、多选答案和原始结果。首次有效完成记录是暂定基准，明确标记「购买基准待核验」。最新安全终止、进行中等状态独立展示，不被旧基准覆盖。
5. 选择本页用户，点击「预览飞书变更」，检查新增/更新字段、原值、新值和阻断原因。单次 API 接受 1–100 个明确 UID；当前页面每页 50 人。
6. 真实目标表核验且写开关启用后，管理员确认预览，再执行同步。重复同步按 UID 更新同一行；订单、企微、用户类型和备注继续由运营在飞书核验维护。
7. 返回「待核验」时先使用「回读待核验结果」。不能用重新创建用户行处理不确定结果。若提示飞书内容变化，则重新预览。

## 字段与权限

当前 `privacyConsent.js` 中的用户授权声明将健康答案与结果限定在 myRoot 内部。本版飞书载荷排除了测评状态、答案、分型、测评 ID 和测评时间，也不发送手机号、昵称、OpenID、UnionID。

| 权限 | 默认角色 | 能力 |
|---|---|---|
| `USER_LABEL_READ` | admin、operator | 查看 UID、访问、来源及映射 |
| `USER_LABEL_HEALTH_READ` | admin | 在 myRoot 内查看个人健康标签 |
| `USER_LABEL_EXPORT` | admin | 预览、执行、回读飞书同步 |
| `CHANNEL_MANAGE` | 现有角色配置 | 保存来源映射 |

查看健康信息使用 POST 读取接口，避免进入 GET 快照缓存；审计记录只保存操作者、动作和返回数量，不复制答案、分型。账号注销、健康授权撤回及到期数据不展示有效基准。

飞书目标字段必须逐项核对。本地按以下字段名和类型校验；缺字段、类型不符、缺单选项或重复 UID 都会阻断写入。附件不能替代实时核验。

| 字段名 | 飞书类型 | 维护方式 |
|---|---|---|
| 用户ID | 文本 | 系统主键，运营不得手工改键 |
| 首次可识别访问日期 | 日期 | 自动；未知留空 |
| 来源活动 | 单选 | 系统建议，保留已识别的人工修改 |
| 来源城市 | 单选 | 同上；是活动城市 |
| 合作方/渠道 | 单选 | 同上 |
| 渠道类型 | 单选 | 同上 |
| 用户类型 | 单选 | 新建默认「待确认」，之后人工维护 |
| 是否下单1元体验装 | 单选 | 新建默认「待核验」，之后人工维护 |
| 是否添加企业微信 | 单选 | 新建默认「待核验」，之后人工维护 |
| 是否复购正装 | 单选 | 新建默认「待观察」，之后人工维护 |
| 标签备注 | 文本 | 人工维护，同步不写此列 |
| 来源依据 | 文本 | 系统维护，保留首次归因、扫码、自报来源及版本依据 |
| 来源核验状态 | 文本 | 系统维护 |
| 系统来源建议 | 文本 | 系统维护，便于与人工来源对照 |
| 数据更新时间 | 日期 | 成功写入时更新，回读核验 |

活动、城市、合作方和渠道类型均应有「待确认」，以及经核验的业务枚举。用户类型应有「内部测试 / 外部真实用户 / 待确认」；订单与企微应有「是 / 否 / 待核验」；复购应有「是 / 否 / 待观察」。具体枚举以真实映射需求为准，程序不会自行新增飞书字段或选项。

目标表已按用户确认完成「首次可识别访问日期」改名，以及订单和企微字段由勾选转为单选；执行前后均核验为 0 条记录，没有历史值迁移。历史未勾选值不能直接认定为已核验的「否」。现有健康列不在同步范围内；飞书返回行后仅保留白名单字段，本实现不展示、保存、迁移或清理这些旧健康列的内容。

## 服务端接入

标签汇总 Module 的 Interface 在 `backend/src/userLabels.js`；同步 Adapter 在 `backend/src/feishuUserLabels.js`。MySQL Store 的检查点构成持久化 Seam；网络 I/O 前提交 PENDING，返回后恢复事务并回读核验。

新增 API 前缀：`/api/v1/admin/user-labels`。

| 方法与路径 | 用途 |
|---|---|
| POST `/query` | 分页查询，`includeHealth: true` 另验健康读取权限 |
| GET `/config` | 映射、来源选项版本、目标字段规格、同步状态 |
| POST `/mappings` | 新增映射版本，校验 `expectedVersion`，复用现有命令幂等与审计 |
| POST `/sync/preview` | 读取飞书全部分页、检查字段、按选定 UID 生成差异及 `planHash` |
| POST `/sync/execute` | 再次核验预览、执行并回读；需要持久化检查点和写开关 |
| POST `/sync/reconcile` | 只回读核对 PENDING/UNKNOWN，不重试创建 |

服务端配置：

| 变量 | 用途 |
|---|---|
| `ROOT_LABEL_FEISHU_APP_TOKEN` | 经确认的多维表格 base token |
| `ROOT_LABEL_FEISHU_TABLE_ID` | 经确认的 `tbl...` 数据表 ID |
| `ROOT_LABEL_FEISHU_ACCESS_TOKEN` | 通过服务端密钥配置注入的有效 API 访问令牌；不得放前端或提交仓库 |
| `ROOT_LABEL_FEISHU_WRITE_ENABLED` | 仅字符串 `true` 开启实际写入，默认关闭 |

当前 Adapter 不负责令牌刷新，第一版由服务端注入有效令牌，过期会停止请求。长期定时同步需另接凭据刷新能力；本次未创建每日同步任务。

只读联调入口：`node backend/scripts/verify-user-labels-feishu-readonly.js`。该脚本使用同一 Adapter，强制关闭写开关，仅允许字段 GET 和官方只读查询/回读 POST，仅输出数量和结构检查结果。2026-09-04 初次云端核查发现标签接口尚未部署、迁移 075 尚未应用、飞书同步配置缺失。应用身份文档授权受阻后，用户选择本人身份并完成授权；22:54 通过 CLI 用户身份连接真实飞书的本地 Adapter 只读联调：22 个字段、0 条记录、所需 15 个字段兼容，无记录写入。2026-09-05 服务端、后台和迁移已上线；用户 OAuth 凭据仍只由本机 CLI 管理，没有复制到云端，因此线上飞书预览和写入保持失败关闭。长期运行仍需安全的 OAuth 凭据管理及续期。详见 [服务端联调记录](myroot-user-labels-server-integration-20260904.md)。

新增迁移 `075_user_labels.sql`：`user_label_mapping`、`user_label_sync_state`。集合同时接入 Store、Projection、快照处置登记、迁移校验和 schema 快照。实际同步仅支持带检查点的持久化 Store，内存演示不会执行真实写入。

飞书 API 参考：[读取字段](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-field/list)、[查询记录](https://open.feishu.cn/document/docs/bitable-v1/app-table-record/search.md)、[按 ID 回读](https://open.feishu.cn/document/docs/bitable-v1/app-table-record/batch_get.md)、[更新记录](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/update)。线上兼容性须以指定表的真实联调为准。

## 同步冲突与恢复

- 已有记录的人工订单、企微、用户类型和备注不进入更新载荷。
- 来源列为空或仍等于上次系统写入值时可更新；其他非空值视作人工修订并保留。系统来源建议另列展示。人工清空来源列不构成永久覆盖锁。
- 执行前重新计算整个预览。每条更新写入前再次读取目标记录，待写字段已变化则停止。飞书原生接口在最后读取与写入之间仍可能发生并发修改，首批导入期间请暂停编辑同批系统字段和用户 ID。
- 每位用户保留最近一次写入前值、拟写值、已确认系统值、record_id 和状态。尚未实现完整批次历史或一键回滚。
- PENDING/UNKNOWN 会阻断后续写入。回读只有在唯一 UID、record_id 及所有拟写字段吻合时才能确认为 SYNCED；否则保留待核验，交由管理员核对。不要删除状态记录来强行重试。
- 需要恢复时，先关闭写开关，依据该次写入前值核对目标记录，仅恢复本次系统修改列；期间人工修改必须保留。回滚应用版本时保留新增两张表和同步状态，不执行删表回滚。

```sh
npm ci --prefix backend

node backend/scripts/dev-user-labels.js
```

测试入口：

```sh
node --test backend/tests/user_labels.test.js backend/tests/user_labels_api.test.js

```

专用 MySQL 集成测试在 `backend/tests/user_labels_mysql.integration.test.js`。只有显式开启 `USER_LABELS_MYSQL_INTEGRATION=true` 时运行；连接读取 `SCHEMA_SNAPSHOT_MYSQL_*` 配置，仅允许回环地址，并确认实例中除系统库外只有空的 `myroot_schema_snapshot_sandbox_marker` 标识库。本地可用 13316，CI 使用其专用服务端口；测试创建并清理临时数据库和随机测试账号。验证实际 MySQL 提交 PENDING 后才调用虚构外部 Adapter，以及中断重启后回读、无重复记录。CI 专项阶段要求一项通过、零跳过。

页面验收已实际检查：查询、健康开关、详情中的多选答案、可读日期与同步预览、禁用实际写入、保存来源映射 v2 后旧用户仍保留 v1 来源。

最终结果：标签单元、HTTP 权限和真实本地 MySQL 集成测试 **19/19 PASS**；项目完整本地检查 **6/6 PASS**。上线后公网 canary、健康、就绪、隐私公告、后台标签查询和同步失败关闭均通过；生产聚合出 62 个用户，两张新表仍为 0 行。证据保存在 `docs/evidence/user-labels-20260904/`。本次没有部署小程序，也没有将本地结果标记为小程序真机验收通过。
