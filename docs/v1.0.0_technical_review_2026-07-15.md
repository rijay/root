## 3. P0 技术发现（发现时快照）

本节记录 2026-07-15 技术评审发现当时的代码事实，用于保留问题 lineage；其中部分缺陷已在后续本地 Implementation 中修正。当前规范状态只以 3.1 节为准，不应把本节的历史证据误读为当前代码仍保持原状。

### P0-01：规范效力与正式 M1 入口仍未关闭

- 证据：PRD `docs/v1.0.0_product_requirements.md:13,50` 明确 `BASELINE_SIGNOFF_PENDING`；V1-T01 要求文档、状态迁移和 Module 绞杀矩阵签字，见 `:1961-1970`。
- 风险：提前冻结状态、数据或业务写链路会让 Implementation 反向定义产品事实。
- 裁决：只允许非运行时 Foundation bootstrap；不得把本轮 Route Registry 工件写成 V1-T03 已关闭。

### P0-02：微信身份头缺少可信入口证明

- 证据：HTTP 响应允许 `X-WX-OPENID/X-WX-UNIONID`，见 `backend/src/app.js:201-208`；登录优先读取原始请求头并直接创建会话，见 `backend/src/domain.js:580-632`；Identity Module 按该 openid/unionid 关联或创建主体，见 `backend/src/identity.js:216-239`。
- 风险：若公网 ingress 未强制覆盖或剥离同名头，调用者可自报身份。当前仓库无法证明这条外部假设成立。
- 修正：建立 Trusted Identity Module；Interface 只接受 `wxCode` 或可验证的平台断言。HTTP Adapter 不把裸头直接提升为身份事实；真实平台断言必须在候选环境取得不可伪造证据。

### P0-03：四类 Admin 写命令遗漏 capability 校验

- 证据：`complete/resolve task` 与 `approve refund/use coupon` 仅通过路径 token Gate，未调用 `requireAdminCapability`，见 `backend/src/app.js:1325-1331,1351-1357`。
- 风险：持有合法 viewer token 的操作者可能执行写动作；role/capability Interface 被路由实现绕开。
- 修正：所有 Admin 命令统一通过 Authorization Module；任务处理使用 `REVIEW_RESOLVE`，退款与券建立精确 capability，并强制 requestId/operator/audit。

### P0-04：`phone_hash` 与 bearer token 实际保存原文

- 证据：`backend/src/identity.js:188-213` 将 `phone_hash` 赋值为手机号；`backend/src/domain.js:285-318` 在 session 与兼容 token map 中保存原始 bearer token。
- 风险：字段名造成错误安全假设；snapshot/DB 泄露会暴露手机号和活跃凭据。
- 修正：手机号使用带版本的 keyed HMAC，只保留 mask + HMAC；session 只存 token hash；先做冲突扫描、dry-run migration 与回退方案，禁止把原文写入迁移日志。

### P0-05：正式运行时可能静默回落 memory Store

- 证据：未配置持久化 Adapter 时 `createConfiguredStore()` 返回 `undefined`，见 `backend/src/server.js:6-20`；`createApp()` 随即创建 memory Store，见 `backend/src/app.js:515-517`；`/ready` 对该 Store 默认可返回 200，见 `:550-572`。
- 风险：配置错误时流量进入易失内存，重启丢数据但 readiness 仍绿。
- 修正：production/cloud runtime 无显式持久化 Adapter 时启动失败；非持久化 Store 的 `/ready` 返回 503；memory 只允许明确 local/test。

### P0-06：Route Policy、参数白名单和客户端版本协商尚未进入运行时

- 证据：旧权限在前后端重复，客户端请求没有 `X-MyRoot-App-Version`/policy version，后端仍返回任意路径字符串；develop/trial/release 当前还共同指向同一生产 CloudBase 环境，见 `miniprogram/config/env.js:4-25`。
- 风险：旧客户端收到未注册路径、未知参数穿透、开关漂移和测试流量污染生产。
- 修正：本轮先建立唯一机器 Registry；后续由同一工件生成/校验前端、后端与 Candidate Manifest digest，并建立独立非生产环境后才接运行时。

### P0-07：通用幂等不是跨实例命令幂等，也没有 outbox/inbox

- 证据：`withIdempotency` 只按 requestId 在当前 snapshot 先查后写，不含 command/actor/request digest，见 `backend/src/app.js:462-478`；PRD V1-T04 要求持久化唯一约束、顺序、重试、死信、checkpoint 和故障注入。
- 风险：同 key 不同 payload 会静默返回旧结果；外部不可逆动作与跨 Module facts 可在 crash/重试/多实例下分叉。
- 修正：Idempotency Module Interface 使用 `{commandName, actorId, key, requestDigest}`；同 scope/key 不同 digest 返回冲突。新增 outbox/inbox/dead-letter/watermark，再接活动、结算、奖励和提醒。

### P0-08：v1 事实与业务唯一约束尚未建立

- 缺失的核心事实至少包括：Health Eligibility、五态 Health Consent、Assessment Session、Activity Session/Enrollment、Privacy Rights Request、v1 Settlement Adjustment、Reward Ledger Event、notification send attempt、migration lineage。
- 风险：直接开发页面写链路只能复用旧单轴/旧 campaign/grant 语义，最终无法满足 PRD Canonical 状态与并发 AC。
- 修正：先完成 V1-T02/T04/T05 的 schema、事务探针、shadow projection、dry-run 和 replay；旧记录只经 Legacy Adapter 读取。

### P0-09：仓库没有 CI 强制执行

- 证据：未发现 `.github/workflows` 或等价流水线；当前验证只在本地手工执行。
- 风险：`17/17 PASS` 不能保证后续每次提交、合并和候选都执行相同 Gate。
- 修正：固定 Node 20，强制 backend tests、miniprogram check、Admin check/build、version alignment、migration checksums、Route Registry digest、dependency audit 和 coverage threshold。

### P0-10：Git 来源与 UED handoff 仍有双重歧义

- 证据：外层仓库 `HEAD=d761ae2`，但 `miniprogram/.git` 仍停在历史 `3930ff0` 并显示大量差异；结构评审也将 UED handoff 标为 `NO-GO / REVIEW_REQUIRED`。

## 4. P1 技术发现

1. **全局 snapshot 锁与吞吐：**所有 `/api/*` 包括 GET 都以 `write:true` 进入 Store，见 `backend/src/app.js:1370-1395`；MySQL 请求在单一 snapshot 上加行锁。当前 Locality 高但吞吐与外部调用持锁风险大。v1 应按事实归属 Module 使用关系事务/outbox，snapshot 退为 Legacy Adapter/投影。
2. **公开浏览不符合 PRD：**活动和商品查询仍要求 token，见 `backend/src/domain.js:696-700,1229-1237`。应增加 public-safe projection Interface，而不是放松私有数据查询。
3. **审计截断：**`auditLogs` 只保留最近 500 条，见 `backend/src/auditLog.js:9-24`，不能作为长期权威审计账本。
4. **代码审查面过大：**`domain.js` 2,976 行、`app.js` 1,425 行、`final-verification.js` 2,622 行；路由、业务事实和验证细节集中，降低 Depth 与 Locality。
5. **数值合同不足：**规则版本、`minCount/minStreak` 等直接 `Number()`，见 `backend/src/settlement.js:119-143,179-193`；缺整数范围、精度、异常值和 property testing。
6. **前端直接路径调用：**现有页面调用 `router.go(path)`，路由参数、返回和恢复动作未由 routeId/allowlist 编译；五 Tab 迁移不能靠替换 `app.json` 完成。
7. **性能验收尚未定义为自动 Gate：**PANE 式全屏大片会放大首屏、包体、解码和弱网风险；需绑定 D-008 的设备/网络/P75 口径并为图片设置授权、裁切、压缩、占位和回退。

### 6.4 Security 与 Command/Event Foundation

本轮新增或加深了以下 Module；每个 Interface 均以失败路径测试作为当前测试面：

1. **Trusted Identity Module**：只有受信 Adapter 返回的 `CLOUDBASE/WECHAT_GATEWAY` 断言可以进入 Identity Module；裸 HTTP 头失败关闭。
2. **Credential Protection Module**：手机号可枚举值使用版本化 HMAC；session 只持久化 token digest；旧 token-map-only 会话不可认证；登录 replay 中的 bearer 记录被清除。
3. **Authorization Module**：任务完成/处理、退款审批、优惠券核销四类命令使用精确 capability，并从认证 principal 取得操作者，调用方 body 不能伪造。
4. **Runtime Persistence Guard**：production/cloud runtime 只允许同时声明 `persistent / transactional / multiInstanceSafe` 的 Store Adapter；错误配置不会以 memory、JSON 或单实例 SQLite Store 假绿。
5. **Command Idempotency Module**：HTTP 写入 Seam 使用 `commandName + actorId + idempotencyKey + requestDigest`；首个直接关系路径不再把网络 `X-Request-ID` 当业务幂等键。版本化 Request Digest Module 使用 canonical JSON 与 keyed HMAC，MySQL Adapter 在构造时强制验证 request/result codecs，不能由调用方逐次选择明文；成功 replay result 使用与持久 command scope 绑定的 AES-256-GCM envelope，并校验 codec/key metadata。请求摘要与命令结果均已采用 current-key 单写、有界 previous-key 按持久 `keyId` 验证/解密；旧 `SUCCEEDED` 可直接 replay，旧 `FAILED/IN_PROGRESS` 在 fenced retry/takeover 中原子升级为 current request key，unknown/retired fail-close。冻结的 `A256GCM:v1` 策略让受保护/本地兼容路径共享 128 KiB 序列化明文上限，固定 canonical base64/ciphertext/envelope 上限；descriptor snapshot 不触发 getter，非法形状、非 UTF-8、缺/错 key、跨 scope 串换、非规范 envelope 或篡改均 fail-close。只有 `protection=A256GCM` 是保留 discriminator，业务结果中的 `tag/ciphertext/bindingDigest` 或其他 `protection` 值不会在本地兼容模式误判。同 scope/key 异 digest 返回 HTTP 409 / `40901`。登录因会返回 bearer，明确不进入通用持久 replay。尚未迁移的 snapshot 路径及外部副作用命令仍必须经 outbox/外部幂等回执或专属 checkpoint 改造。
6. **Event Transport Module**：保留 legacy snapshot 状态转换供既有测试与本地路径使用，同时显式拒绝它消费 migration `006` 完整 envelope；新的 producer MySQL Adapter 只暴露 `stageOutbox / flushBeforeCommit / afterCommit / discard` Interface，并按事务 generation 失效旧引用。关系 Inbox Core 已建立，但尚未由 runtime worker/scheduler 接入生产消费路径。
7. **Task Event Outbox Module 与关系目标 Schema**：`taskEventOutbox.js` 从受信任 task type 推导事件类型，只保留 task event id/type/event type；手机号、openid/unionid、token、健康答案、原始请求均不进入 payload。当前 v1 路径冻结为 `myroot-api + task_event:<id> + position=1 + aggregateVersion=1` 的 singleton partition，拒绝调用方覆盖 source/position；migration `009` 再以 `partition_position >= 1` 防御。该路径级结论不能外推为通用多位置 producer 能力。
8. **Direct Relational Command Recovery Module**：migration `007` 添加 `lease_owner / lease_expires_at / lease_generation`；首个 task command 先提交只含 command claim 的 checkpoint，再以新事务 generation 锁定 owner+generation，执行 task fact、密文结果与 outbox。过期 lease 可被单次 takeover，旧 worker 不能越过 fencing 完成；claim-only checkpoint 若发现 snapshot 或 staged outbox 污染会原子失败。
9. **Command Scope/Crypto Metadata Module**：migration `008` 将 command name、actor、幂等 token 与 digest 改为精确二进制比较，并新增 digest scheme/key、result codec/key、retention policy 与 tombstone metadata。Adapter 对数据库命中结果再次做字节精确检查，覆盖大小写、重音、NFC/NFD 和空白混淆；新命令 request digest 使用 HMAC，历史 `sha256:v0` 只保留兼容验证路径。
10. **CI Gate**：GitHub Actions 主 Job 使用 Node `20.19.4`、`contents: read`、固定超时与并发取消，并以 MySQL `8.0.43` 临时实例依次执行动态 schema snapshot、真实 Runtime Ledger DML/并发/租约恢复集成测试、`v1:foundation:check` 与仓库 `npm run verify`；独立 Node `18.20.8` Job 校验两个 CloudBase 函数的运行时兼容性。workflow 不持有部署 secret、不执行发布。远端 workflow 尚未跑绿，也未设置 required check，因此仍是待关闭 Gate。
11. **Relational Outbox Dispatcher Core Module**：Interface 仅为 `claimDue / completeOwned / failOwned / recoverExpired`；Core 管理新连接、事务、固定 `outbox-retry-v1`、`+08:00` session、未知 commit 的权威回读和不确定连接销毁。事务绑定 Adapter 使用 `FOR UPDATE SKIP LOCKED`、owner+generation fence、版本隔离、payload-free dead-letter companion、完整 envelope 与终态互斥校验；依赖闭包禁止外部投递调用。该 Module 只可由受控 Runtime cycle 调用，未接 Delivery Adapter 或真实外部效果。
12. **Relational Inbox and Checkpoint Core Module**：永久 DDL 已拆为 `010` receipt、`011` checkpoint、`012` INBOX dead-letter，每个 migration 只拥有一个永久 `ALTER TABLE` 和独立 fail-closed preflight。Core 冻结 `RECEIVED/CLAIMED/RETRY_PENDING/SUCCEEDED/DEAD_LETTER/REVIEW_REQUIRED`、checkpoint-first lock order、连续 position、gap/终态 hold、owner+generation fencing、retry/recovery 和 ACK-unknown readback。生产构造只接受默认静态 Registry 解析出的 registration，不开放 caller Registry/factory；transaction toolbox 只开放注册 statement ID 与精确参数、注册 Outbox contract，将 target fact、successor outbox、receipt result/manifest 和 checkpoint 组合在同一事务。`014` 将 receipt 绑定 registration digest，`015` 建立具体 SHARE projection；默认关闭的 Worker Harness 只暴露 `runOnce/recoverOnce/inspect`，并且只可由受控 Runtime cycle 调用；它不提供网络或 Delivery Adapter。
13. **Inbox Content Protection Module**：migration `013` 在空 receipt preflight 后增加 payload/result codec、key id、digest scheme、envelope shape check 与 key-inventory indexes。Durable Core/Adapter construction 只允许 `ready=true / enabled=true` 的保护 Module，不能用 local plaintext compatibility Adapter 落库。payload/result 使用 scope/purpose 绑定的 `A256GCM:v1`，完整性使用 `hmac-sha256:v1`；HKDF 从 secret 分离 encryption/digest 子密钥，有界 previous-key ring 仅用于 decode，payload/result 明文分别限制 64/96 KiB，并在 readback 校验 canonical base64、ciphertext size、codec、key、digest scheme、binding 和 keyed digest。transport payload digest 在认证解密后单独重算，不与持久 keyed digest混用。本地 MySQL 已验证 CHECK/index 结构并增加只读 Key Inventory Foundation；该 Implementation 仍缺 Candidate/生产 inventory、rotation/retention Job、数据兼容性、查询计划和运行密钥证明。
14. **Governed Replay Modules**：`016/017/023` 建立具名 run、硬 TTL/数量上限、冻结 cursor、generation `>=2` shadow projection 与 executor behavior identity。生产 Registry 只从仓库静态 manifest/source 解析；SQL contract 使用精确 statement digest/placeholder/table allowlist；Control 与 Runner 默认禁用且在 commit ACK unknown 时销毁不确定连接后权威回读。无 Outbox、无网络、无自动生产切换。
15. **Outbox→Inbox Bridge Harness**：只接受已注册的静态 SHARE scope，先持久化 Inbox Receipt 再完成 Outbox；active unregistered scope 会 fail readiness。只读 inspect 以 scoped DEAD source、linked scoped source 与 self-claimed scoped OUTBOX 三个独立锚点核对 companion，历史 active/dead/terminal 与 OPEN companion 的漂移都阻断 readiness。Harness 默认禁用，只可由受控 Runtime cycle 执行；本地已有默认 preview 的专属 scheduler 配置，但尚无真实 timer 部署、告警接收端或正式流量接线。
16. **Notification Delivery Core**：`018`～`022` 建立 subscription attempt/grant/job/send attempt/transition；`024`～`027` 收紧原生决定枚举、请求 identity/唯一性与 receipt keyed-HMAC metadata。Core 拥有事务、fencing、精确关联和 ACK-unknown 收敛，默认禁用且不包含真实微信网络发送。
