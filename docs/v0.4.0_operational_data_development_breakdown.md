## 1. 目标

把 V0.4.0 从产品规格拆成可执行开发批次，优先解决当前线上最影响普通用户使用的三件事：

1. 云托管重启后数据不丢。
2. 用户登录态可保持，session 失效和网络失败有清晰处理。
3. 运营每天上传有赞订单 CSV 与物流 CSV 后，系统可按微信授权手机号自动匹配用户，并支持必要人工修正。

本轮拆单不直接开始编码，但每个批次都给出目标文件、Module、Interface、验收和验证方式。

## 2. 开发原则

- P0 先稳生产地基：MySQL Store Adapter、Session Module、后台最低访问保护优先于 CSV 体验细节。
- 保持当前 Store Interface：P0 先新增 MySQL snapshot Adapter，不重写全部业务读写模型。
- 新能力优先沉到深 Module：CSV 解析、手机号归一化、状态映射、批次锁定、自动匹配和审计不散落在 `admin.js`。
- 后台页面只消费整理好的展示数据，不直接拼业务判断。
- 所有写操作必须可重复、可追溯、可失败恢复。
- P0 不引入多运营账号和复杂权限，但线上后台必须有最低访问保护。

## 4. 目标 Module 与 Interface

### 4.1 Store Module

文件：

- `backend/src/store.js`
- `backend/src/mysqlStore.js` 或继续在 `store.js` 内导出 MySQL Adapter
- `backend/db/schema.sql`
- `backend/scripts/migrate-store.js`
- `backend/scripts/verify-store.js`

新增 Interface：

- `createMysqlStore(config, options)`
- `exportSnapshot()`
- `importSnapshot(snapshot)`
- `validateSnapshot(snapshot)`
- `getStoreHealth()`

P0 实现策略：

- 先实现 MySQL snapshot Adapter，保持当前 `data` 对象读写方式。
- MySQL 中保存完整 JSON payload、schema version、updated_at。
- 这样可以先获得持久化和 session 稳定性，避免在 V0.4.0 P0 重写所有领域数据读写。

### 4.2 Session Module

文件：

- `backend/src/session.js`
- `backend/src/domain.js`
- `miniprogram/utils/request.js`

Interface：

- `createSession(data, userId, context, now)`
- `verifySession(data, token, now)`
- `expireSession(data, token, reason, now)`
- `refreshSession(data, token, now)`
- `buildAuthError(code, requestId)`

职责：

- 替代分散的 `data.tokens[token] = userId` 直接写法。
- token 写入持久化 Store。
- 输出标准错误码：`SESSION_EXPIRED`、`SESSION_INVALID`、`AUTH_REQUIRED`、`CONTAINER_UNAVAILABLE`、`NETWORK_FAILED`。

- `requireAdmin(req, env)`

- `buildAdminAuthError(requestId)`

P0 策略：

- 所有 `/api/v1/admin/*` 写操作必须校验。

## 19. 开发风险与控制

### R1 MySQL Adapter 牵动面过大

控制：

- P0 使用 snapshot Adapter，保持当前 Store Interface。
- 不在 P0 重写所有领域数据读写。

### R2 session 错误契约破坏现有小程序请求

控制：

- 保持现有成功响应结构。
- 错误分支新增标准错误码。
- 小程序 request 层集中适配。

### R3 CSV 导入与真实样本导入重复

控制：

- Csv Import Module 复用现有字段映射能力。
- 运营入口隐藏 Adapter 术语。
- 开发与发布 tab 保留真实样本导入。

### R4 自动匹配误绑定

控制：

- 只允许唯一用户、唯一有效订单自动绑定。
- `buyerPhone` 不单独触发自动绑定。
- 多订单、多用户、已绑定、进行中订单全部进入冲突队列。

### R5 后台敏感数据暴露

控制：

- P0 做最低访问保护。
- 列表默认脱敏。
- raw payload 只在受控详情中展示。

## 20. 开放问题

1. 生产 MySQL 是使用微信云托管内置 MySQL，还是独立云数据库实例。
2. `ROOT_ADMIN_TOKEN` 是否接受作为 v0.4.0 的最低后台保护方式。
3. MySQL snapshot Adapter 是否作为 P0 方案确认，规范化多表存储是否后移。
4. 迁移窗口是否允许短暂停止 CSV 导入和后台写操作。
5. 小程序端是否需要在 v0.4.0 展示物流公司和运单号，还是保持 P2。
